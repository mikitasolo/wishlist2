# AGENTS.md

Working instructions for AI agents (and humans) contributing to this repo. Keep this file current when conventions change.

## Project

A wishlist app: **Next.js 16 (App Router), React 19, TypeScript, MongoDB/Mongoose, NextAuth v5 / Auth.js (database sessions), Tailwind v4, Vercel Blob**. Package manager is **npm**. Path alias `@/*` maps to the repo root.

## Commands

```bash
npm ci               # install deps (Conductor's setup script runs this for you)
npm run dev          # local dev server — in Conductor: npm run dev -- --port $CONDUCTOR_PORT
npm run lint         # eslint — must pass before done
npm run format:check # prettier --check — must pass before done (npm run format fixes it)
npx tsc --noEmit     # typecheck — must pass before done
npm run test:cov     # full Vitest suite (unit + component + API) + the coverage floor in vitest.config.mts — must pass before done
npm run build        # production build — must pass before done
npm run check:trace  # after a build: sharp's native libvips ships with every route that ships sharp (the upload route, share cards), and NextAuth's route ships none (CI runs it)
npm run smoke:deploy -- <url>  # read-only GET smoke of a deployed host (auth + upload routes start, a share card draws); safe on staging
npm run generate:email-logo    # re-render the email logo (lib/emailLogo.ts) from app/icon.svg; rerun when the logo changes
npm run test:e2e     # Playwright end-to-end suite
npm run test:watch   # watch mode
npm test             # the same suite without coverage
npm run release:preview  # list commits remote staging is ahead of remote main (dry run)
npm run release          # promote: fast-forward remote main to remote staging — operator only
```

## How work flows

Tasks live in **Linear** — workspace `mikitasolo`, team **Wishlist**, issue keys `WIS-<n>`. Each issue is worked in its own **Conductor** workspace (a git worktree + branch cut from `staging`), usually by an AI agent. The human is the **operator**: they write and clarify requirements, review, merge, and release.

### Branches

- **`staging`** is the default and integration branch. Every change reaches it through a **pull request**, which the operator **squash-merges**. CI (`ci.yml`, `e2e.yml`) runs on every PR; `audit.yml` runs only on a PR that changes `package.json` or `package-lock.json`, plus daily on `staging` and on demand (see the `overrides` item under Conventions). **Vercel builds only `staging` and `main`** (`git.deploymentEnabled` in `vercel.json`): a PR branch gets no preview deployment, because on the Hobby plan a busy day of PR pushes used up the daily deployment cap and left `staging` itself undeployed. Vercel matches those keys as minimatch globs, where `*` stops at a `/`, so the catch-all is `"**"`: with `"*"` every `nikitasolo1134/wis-…` branch still deployed (WIS-185). `test/unit/vercelConfig.test.ts` pins which branch names build. CI is the PR's check; a change's first real Vercel build is its `staging` deploy, so smoke `staging` after a merge that touches the build, env or runtime setup.
- **`main` is production** (Vercel deploys on push). It only ever moves by **fast-forwarding to `staging`** (`npm run release`, i.e. `git push origin origin/staging:main`) — never commit to `main`, never open a PR into it. This keeps `main` a strict prefix of `staging` (identical hashes, no divergence).
- **A push to `main` is a release.** `.github/workflows/release-notify.yml` posts the changelog to a Telegram channel (built from the commit subjects in the pushed range by `.github/scripts/telegram-release-notes.py`) and moves the Linear issues those commits close from **On Staging** to **Done** (`.github/scripts/linear-mark-released.py`). Secrets: `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` / `LINEAR_API_KEY`; without them each job prints a preview and changes nothing.

### Issue statuses

| Status      | Meaning                                         | Moved by                                    |
| ----------- | ----------------------------------------------- | ------------------------------------------- |
| Backlog     | Idea, or not specified well enough to build yet | operator                                    |
| Todo        | Spec is ready — an agent can take it            | operator                                    |
| In Progress | Being worked in a workspace                     | the agent, when it starts                   |
| In Review   | PR is open                                      | Linear's GitHub integration                 |
| On Staging  | Squash-merged into `staging`, not yet released  | Linear's GitHub integration                 |
| Done        | Released to production                          | `release-notify.yml`, on the push to `main` |
| Canceled    | Won't do                                        | operator                                    |

Labels: one **Type** (Feature / Bug / Improvement / Tech debt — maps to the commit prefix) and one **Area** per issue. Large features are Linear **projects**; their design notes and open questions live in the project description, so read it before starting an issue inside one.

### Agent lifecycle for an issue

1. **Read the issue** (`WIS-<n>`) through the Linear MCP server — description, comments, and the parent project's description if it has one. If the acceptance criteria are missing or ambiguous, especially anywhere near the domain invariants below, **ask the operator before writing code**. Don't guess at product decisions.
2. **Move the issue to In Progress.**
3. **Stay in your workspace branch.** Conductor created it from `staging`; don't rename it, and never check out, commit to, or push `staging` or `main`.
4. **Implement with tests** (see Testing policy). Stay in scope: an unrelated bug or idea you notice becomes a **new Linear issue in Backlog** (link it from the PR), not part of this change.
5. **Verify**: everything marked "must pass before done" under Commands passes locally, plus `npm run test:e2e` if you touched a flow the E2E smoke tests cover.
6. **Review your own diff** (`git diff origin/staging...`) as a skeptical reviewer would — correctness, the domain invariants, missing tests, leftover debug code, docs the change makes stale — and fix what you find.
7. **Commit, push your branch, and open a PR into `staging`** (`gh pr create --base staging`), following the rules below.
8. **Get CI green** (`gh pr checks --watch`) and fix failures. Branch protection isn't available on the free GitHub plan, so nothing else stops a red PR from being merged.
9. **Hand off**: reply with the PR link, what changed, how you verified it, and anything the operator has to do by hand (env vars, migrations, dashboard config).

**Operator-only** — never do these as an agent: merge a PR, run `npm run release`, run a migration against a deployed host, change env vars or secrets in Vercel/GitHub, or push to any branch other than your own.

### Pull requests & commit messages

**PR titles are published.** A PR is squash-merged, so its title becomes the commit subject on `staging`, and every subject in a release goes verbatim into the Telegram changelog. The title is release-note copy, not a note to yourself:

- **Conventional-commit prefix**, which the changelog groups by: `feat:` `fix:` `perf:` `refactor:` `docs:` `test:` `build:` `ci:` `chore:`. Anything unprefixed lands in a catch-all "Other" section — avoid it.
- **Imperative, specific subject** that stands alone. A reader in the channel sees only the subject, with no diff and no body: `fix: release a member's bookings when they're made an owner`, not `fix: bug` or `fix: address review comments`.
- **No issue ID in the title** — the channel's readers don't have Linear. Put `Closes WIS-<n>` in the **body**: that links the PR to the issue and drives its status. Use `Part of WIS-<n>` for a PR that doesn't finish the issue.
- **The body becomes the squash commit's message**, so it explains _why_, plus anything a future reader would otherwise have to reconstruct: the invariant being protected, the failure mode being closed, migrations the change requires and their ordering, how it was tested. Follow `.github/pull_request_template.md`.
- **One issue, one PR, one coherent change.** "Various fixes" is one useless changelog line covering several things worth naming. Commits inside the branch can be as granular as you like — they're squashed away — but still use the conventional prefixes.

### Parallel workspaces

Several agents run at once, each in its own worktree. Don't assume anything is exclusive to you:

- **Ports**: dev runs on `$CONDUCTOR_PORT` (the Conductor run script passes it); E2E derives its port from `CONDUCTOR_PORT` too (`playwright.config.ts`). Never hard-code 3000/3100.
- **`next dev` leaves `AGENTS.md` alone**: Next 16.3 appends a managed "nextjs-agent-rules" block to it whenever it detects an AI coding agent, which left every workspace with an uncommitted change. `agentRules: false` in `next.config.js` turns that off; keep it.
- **Conflicts**: other PRs touch `README.md` / `AGENTS.md` too. When yours conflicts, rebase onto `origin/staging` and force-push **your own branch** with `--force-with-lease`; don't merge `staging` into it.
- **Local dev data**: workspaces get the repo root's `.env` / `.env.local` copied in (`.conductor/settings.toml`); `.env.prod` / `.env.staging` deliberately aren't. The dev MongoDB is shared by every workspace — don't wipe or bulk-edit it. Prefer the test suites (in-memory Mongo, mocked email) over poking the dev server. When you do run it, use `EMAIL_TRANSPORT=console`: every email (the magic link included) is printed to the dev-server log instead of sent, so no SMTP credentials are needed and no real mail goes out. Only that transport ever prints an email's recipient or link; the `smtp` path in `lib/email.ts` must never log them, not even in a send error. A printed magic link is a working sign-in credential, so `lib/env.ts` allows `console` only where `VERCEL_ENV` is unset (local dev, CI, E2E) or `development`, and refuses it on Vercel Preview and Production.

## Testing policy (required)

**Add or update tests for every change that touches logic — no exceptions for "small" fixes.** The booking flow, currency conversion, privacy gating, and invite/gift lifecycle are exactly the kinds of things that broke before and must stay covered.

- **New pure logic** (`lib/utils/**`, Zod schemas in `lib/validations.ts`) → a unit test.
- **New/changed interactive component behavior** (conditional rendering, state, optimistic updates) → a component test. Skip purely presentational markup.
- **New/changed API route with authorization or business rules** → an API test (in-memory Mongo + mocked session).
- **Every bug you fix** → a regression test tagged with a `// regression:` comment citing the cause, so it can't silently come back.
- Before considering work done: everything marked "must pass before done" under Commands passes — the same checks CI runs.

Chase meaningful coverage of logic/authorization, not a headline line-coverage number.

### Test layout & harness

- `test/unit/**` — pure functions and schemas (node env, no DB).
- `test/components/**` — React Testing Library; **add `// @vitest-environment jsdom`** as the first line.
- `test/api/**` — route handlers against a real in-memory MongoDB. Pattern:
  - `vi.mock('@/lib/mongodb', ...)` → no-op `connectDB` (the shared mongoose connection from `test/db.ts` backs the models).
  - `vi.mock('@/lib/auth', () => ({ auth: vi.fn() }))`, then `const session = vi.mocked(auth)` to control the session (NextAuth v5 — routes call `auth()`, not `getServerSession`).
  - Mock `@/lib/email` / `@/lib/utils/currencyRates` when a route would otherwise send mail or hit the rates API.
  - `connectTestDB` / `disconnectTestDB` / `clearTestDB` from `test/db.ts` in `beforeAll` / `afterAll` / `beforeEach`.
- **Mock lifecycle (Vitest 5).** Every mock's call history is cleared before each test (`clearMocks` is on by default and runs before `beforeEach`), but its implementation isn't: `vi.restoreAllMocks()` only puts back what `vi.spyOn` replaced, and leaves a `vi.fn()`'s `mockResolvedValue` / `mockImplementation` in place for the next test (Vitest 3 used to reset those too). So a shared `vi.fn()` that tests configure (the mocked `auth`, `sendEmail`, `fetch`) gets a `mockReset()` in `beforeEach`, as the API tests do with `session.mockReset()`. `vi.mock` / `vi.hoisted` must sit at the top level of the file (nested, they throw), and an un-awaited `expect(…).resolves` / `.rejects` fails the test.
- Vitest config injects dummy env vars (see `vitest.config.mts`) so import-time env reads don't throw. Vitest only picks up `test/**/*.test.{ts,tsx}`; Playwright specs live in `e2e/**`.
- `e2e/**` — Playwright (`npm run test:e2e`). `e2e/global-setup.ts` starts an ephemeral MongoDB, seeds a user who owns the `e2e-birthday` list and is a member of another user's `e2e-friend` list (so specs can take either side), plus a database session (writing a `authjs.session-token` storageState so the `authed` project is logged in without magic-link), and unused magic-link tokens (`e2e/magicLinks.ts`: three for emails with no account yet, one for the friend, plus a session for the friend) so a spec can sign up or sign in through Auth.js's real callback without any email (each link works once), then builds and starts the app; `global-teardown` stops both. Specs are `*.public.spec.ts` (signed-out) or `*.authed.spec.ts` (signed-in). Every spec, a new one included, imports `test` and `expect` from `e2e/fixtures.ts`, never from `@playwright/test` (ESLint refuses it; types may still come from there). Its `test` fails a spec whose pages throw an uncaught error (`pageerror`, an unhandled promise rejection included), which can't be allowed, or log a `console.error` that isn't allowed. A failure the spec provokes on purpose (a request it answers with an error status or aborts, which the browser logs as `Failed to load resource`, and the app's own log line for it) is allowed in that spec with `consoleErrors.allow(failedRequest(/…path…/), /^Error updating item: /)`, matched as narrowly as it can be. A context the spec opens itself (`browser.newContext()`) is only guarded once handed to `consoleErrors.watch`. The suite-wide `ALLOWED_CONSOLE_ERRORS` there is only for an error no spec can avoid, each entry with a comment saying why and which issue tracks it; it's empty today. Keep E2E to a few resilient smoke tests per flow — unit/component/API tests carry the detailed coverage.

## Domain invariants — do not regress

These are correctness/privacy rules the product depends on:

- **A wishlist has exactly two kinds of people: owners and members.** There is no `admin` tier — a manager of someone else's list isn't a relationship the product needs, so anyone trusted to manage a list is a co-owner. Owners live in `Wishlist.owners[]`; members are rows in `WishlistMember`, which carries **no role field**. Membership is existence, not a level.
- **All co-owners are equal.** Identical authority (including deleting the list), the list shows on each of their profiles, and none of them ever sees booking status. Authorize owners only through `isWishlistOwner` / `ownedByFilter` / `primaryOwnerId` from `lib/utils/wishlistOwners.ts`, or `getOwnerAccess` / `isOwnerOfWishlist` from `wishlistAccess.ts` — never by hand-rolling a check on `owners[]`. A list must always keep at least one owner: take an owner off only through `removeWishlistOwner` (`lib/utils/wishlistOwnership.ts`), whose single conditional write refuses the last one and refuses an actor who is no longer an owner, and stop before any side effect unless it returns `'removed'`. An `isLastOwner` check or an owner check on the caller against an earlier read is only a pre-check — on its own it races (two co-owners leaving at once both pass it; so do two owners removing each other), and the schema's non-empty validator doesn't run on `updateOne`. The same goes for the caller of an owner-only write: deleting a list is one `findOneAndDelete`, and editing it (settings and the `featured` pin together) one `findOneAndUpdate`, each filtered on `ownedByFilter(callerId)`, and nothing else is touched unless it matched. Where the writes live on other collections and so can't carry the check (kicking a member, inviting or promoting someone), re-read ownership right before the first change. That only narrows the race to the gap before the next write, so prefer a conditional write whenever the write is on the `Wishlist` itself. A caller who lost ownership mid-request gets the same answer as any non-owner.
- **Members have no management powers.** They browse, propose items, and book gifts. They can't see the members list, drafts, wishlist settings, or publish an item directly. Everything else is owner-only.
- **Owners never see booking status.** For any owner, `booked` folds into `available`; never reveal who booked what.
- **"N items" means a list's published items, on every screen.** That's available, booked and completed, with booked folded in for everyone, so no count anywhere says how much is reserved. Count with `lib/utils/itemCounts.ts` (`isPublishedItem`, `tallyItems`, the formatters), or on the server with `countWishlistItems` (`lib/utils/wishlistItemCounts.ts`), never with a status filter of your own. Drafts and proposals to review are counted only for an owner on an owner surface ("11 items · 2 drafts · 1 to review": the `draftCount` / `proposalCount` that `GET /api/wishlists` puts on your own lists only), so a member never sees a draft or anyone's proposal counted. The share card counts the same set (`isCountedOnShareCard`), so changing the set also changes which writes have to purge it. `test/api/itemCounts.test.ts` checks that every source gives one list the same count. Item totals across your lists leave archived lists out (the dashboard; `/items` unless you ask for them).
- **Becoming an owner requires consent and releases your bookings.** The three ways in are: create the list, accept an `owner` invite (`POST /api/wishlists/[id]/members` by username), or accept a promotion (`POST /api/wishlists/[id]/owners/[userId]`, which issues the same kind of invite — never a silent role write). The `/members` invite honours the invitee's `whoCanInvite`; promotion skips it, so it is only ever issued to an **existing member** (404 for anyone else, identical whether or not the user exists). On accept, `addWishlistOwner` frees the items that person booked **and deletes their reservations** — an owner can't be their own gifter. This is the one place that deletes a reservation on a membership change; leave/remove deliberately keep it (a booking that loses the race to one only ends the reservation it wrote itself: see the next item).
- **A booking must never be left where nobody can release it.** Only the holder can cancel a booking, and owners are booking-blind — so becoming an owner has to free their booked items first, or the item sits claimed forever (invisible to them, hidden from the owners, unbookable by everyone else). Route role transitions through `releaseHoldingsForRole` (`lib/utils/wishlistOwnership.ts`): → owner frees items **and** cancels reservations; → member does nothing (members manage their own bookings). Leave/remove free the items and keep the reservation, so the gifter can still log a gift they went on to give. Demotion and visibility changes need nothing — members retain access at every tier, and only members can book. A booking in flight is the other half: the item route reads the caller as a member at the top of the request, so once a member's booking has written the item and its Reservation, `undoBookingUnlessMember` (`lib/utils/lateBooking.ts`) re-reads their role. If they've since left, been removed or become an owner, or the list was archived, it frees the item and ends the Reservation it wrote (one it overwrote is put back, unless they're now an owner), and the request is refused. That re-check only closes the race because becoming an owner grants the ownership before it releases, and a member's leave or kick frees their bookings again after the membership delete (`releaseLateBookings`). A new way off a list, or into its owners, keeps the same order.
- **Never report a released-booking count to an owner.** "2 items released" tells them how much of the list was reserved. Counts only go back to the gifter themselves (invite accept, leave).
- **Being demoted, removed or kicked tells you, and only you.** A demotion sends the demoted owner a `role_changed` notification (linking to the list), and removing an owner or kicking a member sends a `removed_from_wishlist` one (with no link, since the list may now be hidden from them). Deleting a list notifies nobody: it clears that list's notifications instead, and `createNotification(s)` (`lib/notifications.ts`) takes back one written for a list that's gone by the time it lands, so write a list's notifications only through them. Each goes out only once its write has landed, never for a refused or lost one, and never for leaving. Neither names the owner who did it (`createNotification` drops any actor for both types, as it does for proposals), mentions bookings, or reaches the other owners.
- **Losing ownership clears the per-owner state.** Demote, remove, or leave pulls the user from `owners` **and** from `featuredBy`. Only owners may change ownership, and nobody may change their own role.
- **Leaving a list or losing a role on it cancels your pending invites for it.** Accepting an invite grants the role it names, and it can't just refuse non-members (`owner` invites legitimately go to them), so a leftover one would let the person removed undo it, e.g. a kicked member accepting a pending promotion and coming back as a co-owner. Leave, kick, remove-owner and demote therefore call `cancelPendingInvites` (`lib/utils/wishlistInvites.ts`). An owner write (remove-owner, demote, a co-owner leaving) calls it once the write has landed, never before it and never when `removeWishlistOwner` refused it. (A co-owner's leave that it refused because a demotion has just made them a member goes on as that member's leave, which calls it as below.) A kick or a member leaving calls it both before its membership delete and after it, and answers 404 instead of success when that delete matched nothing. It deletes only that person's _pending_ invites for that list (accepted/declined rows stay) plus their `wishlist_invite` notifications for it, the latter best-effort.
- **An invite is answered by claiming it, before anything is granted.** Accept and decline record the answer in one conditional write on the pending invite, and answer 404 when it matches nothing. Once the answer has landed (an accept's once the role is granted), `recordInviteAnswer` (`lib/notifications.ts`) writes it onto the invitee's own `wishlist_invite` notification and marks that read, best-effort, so it reads "You joined …" or "You declined the invite to …". Notifications carry no invite id, so it picks the row by time: written between the invite and the answer. An owner's cancel and a removal's `cancelPendingInvites` are conditional deletes on that same pending row, so exactly one of any of them racing lands. If granting the role then fails, the claim is reopened (back to `pending`), and accepting again finishes the job. A promotion invite carries `promotion: true` (set only by `POST /owners/[userId]`), and accepting it, or any `owner` invite whose invitee is a member, goes through `promoteMemberToOwner` (`lib/utils/wishlistOwnership.ts`). That takes the membership row in one conditional delete before it grants ownership. Kick and leave delete that same row, so a removal and a promotion can't both land. When the row is already gone, nothing is granted and the claimed invite is withdrawn (`withdrawInvite`): a promotion never makes a non-member an owner, whenever they left. A promotion also re-checks the membership once its invite exists, and withdraws the invite with the same 404 if the member has gone (but not if they've already accepted it, which takes the row too). An accept that loses to a list delete grants nothing either. Deleting a list removes the list before its memberships, so joining checks the list _after_ its membership upsert and takes the row back if the list is gone. `addWishlistOwner` / `promoteMemberToOwner` return `null` when their ownership write matched no list, and skip the booking release, which on a deleted list would only destroy reservations the delete keeps on purpose. Either way the claimed invite is withdrawn, and the answer is the 404 `This wishlist no longer exists`.
- **"Featured" is per-owner** (`Wishlist.featuredBy[]`), not per-list: on a co-owned list one owner can pin it to their dashboard without touching anyone else's. API responses fold it to a boolean `featured` for the caller via `serializeWishlist`.
- **Never expose user emails to other users.** Invite/notification emails are used server-side only. When someone may have no username, name them to others with `publicDisplayName` (`lib/utils/displayName.ts`: username, then `name`, then "Someone"), never with any part of their email. That goes for defaults too: a username is public, so a generated one (`generateUniqueUsername`, `lib/utils/username.ts`) is a random `user_<8 base36>` handle and the generator takes no input at all, so it can't derive one from the email. (Accounts created before this rule kept the handle they had: nothing renames them.)
- **Invites are registered-users-only** (by username). There is no email-invite path; invites match `invitedUser`.
- **One pending invite per person per list, and an issued invite never hinges on its email.** Issue invites only through `issueWishlistInvite` (`lib/utils/wishlistInvites.ts`). A unique partial index on `WishlistInvite { wishlist, invitedUser }` (`status: 'pending'`) refuses a concurrent duplicate, which is answered as "already pending" with no second email or notification. Partial on purpose: accepted/declined rows are kept, and a declined invitee can be invited again. Once the invite exists its notification is created regardless, and a failed email is caught and logged but doesn't fail the request.
- **Proposals are anonymous to the owner.** Owners never see who proposed an item (`proposedBy` is hidden in the items API), and this extends to notifications: the `proposal` notification carries `actorUsername: null` and renders as "Someone proposed…". Never surface the proposer to the owner anywhere. Owner-facing notifications fan out to **every** owner (`createNotifications`).
- **Gifting is decoupled from the live item.** Booking creates a durable `Reservation` (survives owner status changes and leave/kick). Marking a gift writes a permanent `GiftLog` and deletes the reservation but **does not modify the owner's item**. Owner status changes (`complete`/`draft`/reopen) clear `bookedBy` but must **not** delete reservations. A member's own book and unbook write the item first and their Reservation second, through `writeBookingReservation` + `settleBookingReservation` / `cancelUnbookedReservation` (`lib/utils/bookingReservations.ts`), which re-read the item afterwards. If the same person's book and unbook from two tabs crossed, the Reservation is put back the way the later of the two would have left it: a booking that was released by their own unbook (or by their becoming an owner) deletes the Reservation it just wrote, and an unbook whose item they've booked again writes it back. What keeps a Reservation on purpose still keeps it: an owner's status change, the item's deletion, leave/remove. **The Reserved page releases an active reservation through that same unbook**: its Release sends `PATCH /api/items/[itemId]` (the item id comes from the reservations read), never a path of its own that frees an item, so `cancelUnbookedReservation` settles the Reservation as it does for an unbook from the list. A refused unbook (no longer a member, no longer their booking, the list out of their reach) says so and reads the page again. A card is active only while the item is booked by the gifter (`stillReserved`) on a list they can still open (`listOpen`: `readReservationWishlists` has it, so it's their own access, never the `archived` flag), since the item route refuses everyone else. Any other card needs their confirmation, and only those offer Dismiss (`DELETE /api/reservations/[id]`), which ends just that Reservation and never touches the item. One still reserved to them on a list they can't open (archived, say: only an owner can release it then) says "This list is no longer available to you", never why, and "No longer reserved to you" is kept for an item that really isn't theirs any more (`reservationNote`, `lib/utils/reservations.ts`). **A gift given stays given on the list**: marking it leaves the item booked by the gifter, so a member's own items read (`GET /api/wishlists/[id]/items`, and their own `PATCH` answer) flags with `givenByMe` each item whose booking they hold and have marked as given: their gift history has the item, and they hold no Reservation for it, since marking a gift ends the booking's Reservation and a later booking of the same item writes a new one (`itemsGivenBy`, `lib/utils/giftHistory.ts`, best-effort), and the card shows "Given by you" in place of Unbook, with Release… in its menu behind a warning that someone else could then buy it again. It's read only from the viewer's own `GiftLog` for their own bookings, and never computed for, or present in, an owner's or a visitor's answer.
- **Editing an item never changes its status.** Status changes are explicit actions (publish / move-to-draft); a content edit must not clobber a booking.
- **Archived wishlists are owner-only** — 404 for everyone else, including direct links (any owner still sees them). That covers its items too: listing them, proposing, booking or unbooking, and editing or withdrawing a proposal. **A list and its items share one set of view rules**: `GET /api/wishlists/[id]` and `GET /api/wishlists/[id]/items` both admit a viewer through `getWishlistViewAccess` (`lib/utils/wishlistAccess.ts`: archived, visibility tier, membership, any owner's friends), so a new read that admits viewers to a list uses it too rather than re-deriving the rules. The item writes (`POST /api/wishlists/[id]/items`, `PATCH`/`DELETE /api/items/[id]`) refuse a non-owner on an archived list with `isHiddenByArchive`, answered like a missing list or item. So does every owner-only route on the list itself (its settings and delete, members, invites, kick, owners): `getOwnerAccess` hands no list back to a non-owner of an archived one, so they get exactly the `Wishlist not found` 404 of a list that doesn't exist, never the 403 that would confirm it does. That includes an owner who lost ownership mid-request, because the read that picks a refused owner write's answer goes through `getOwnerAccess` too. A non-owner of a list that isn't archived still gets 403. These routes check the session before they look the list up, so a signed-out caller gets the same 401 whether or not it exists, and the invite route rate-limits only once the caller is known to own the list. A new owner-only route on a list authorizes its caller through `getOwnerAccess` (not the bare `isOwnerOfWishlist`, which can't tell a hidden list from a refused caller) and keeps the same order; `test/api/archivedOwnerRoutes.test.ts` holds a table of these routes to add it to. Leaving (`DELETE /api/wishlists/[id]/members/me`) is the one exception for members: they may still leave an archived list, as any other (their bookings are freed and their pending invites cancelled), since that only takes their access away. But the leave route also checks the session first, and answers anyone else who isn't on an archived list with that same `Wishlist not found` 404, never `You are not a member`. That includes someone taken off it mid-request, so the answer comes from a fresh read through `getOwnerAccess` (`test/api/archivedLeave.test.ts`). A co-owner whose leave finds they've already lost ownership is anyone else by then: if a demotion left them a member, they leave as one.
- **Search returns only lists the searcher could open.** `/api/search` matches lists with `viewableWishlistsFilter` (`lib/utils/wishlistAccess.ts`), the query form of `getWishlistViewAccess`, for a listing that can't check each document one by one. A table test over every visibility / archived / relationship combination (`test/api/viewableWishlistsFilter.test.ts`) pins the two together, so change them together. A list the searcher doesn't own or belong to also stays out of their results if any of its owners shows their wishlists to friends only and the searcher isn't that owner's friend. The Booked page's reads of a gifter's reservations and gift history (`readReservationWishlists`, `lib/utils/reservationWishlists.ts`, which `giftWishlistSlugs` in `lib/utils/giftHistory.ts` goes through too) use the same filter, inside their one query for the lists, to return a list's live slug and occasion only while the gifter can still open the list: a Reservation or GiftLog outlives leave, kick, archiving and a list going private, and none of those may leave the gifter seeing the list's date, or its current slug (made from its name, and an owner can change it). Otherwise they're `null`, and a reservation's card links the list by its id. Only the snapshot the record took, the list's id and, for a reservation, its item's id (which Release unbooks), whether the gifter can still open the list (`listOpen`) and the live item's status (whether that should stay is WIS-124) come back regardless.
- **`profileVisibility: 'friends'`** hides the bio and the browsable wishlist list from non-friends, but keeps username/avatar public. Per-wishlist visibility is a separate axis and is never bulk-mutated as a side effect.

## Conventions

- **Money** is stored as integer **cents**. Currency-code casing is **not uniform** in the DB: `Item.price.currency` is lowercase (to match the rates format), while `Wishlist.currency` and `User.defaultCurrency` are uppercase — normalize before comparing. Conversion routes through USD (`rate` = units per USD). Use the shared helpers in `lib/utils/currency.ts` / `currencyRates.ts`.
- **A user's currency is suggested, never guessed for them.** Every account starts on `defaultCurrency: 'USD'`, and the dashboard's one-time prompt (`components/CurrencyPrompt.tsx`) offers anyone still on it who hasn't answered it yet (`currencyToOffer`) the currency of where their browser is. `suggestCurrency` (`lib/utils/currencySuggestion.ts`) works it out in the browser only, from the time zone, then the language's region, and only ever suggests a currency in `CURRENCY_OPTIONS`: no IP geolocation, no server-side `Accept-Language` guess. A zone that names a place decides on its own (one in a country whose currency we don't offer suggests nothing, rather than what the language says), and a USD suggestion shows no prompt. Either answer sends `currencyChosen: true` to `PATCH /api/users/me`, which stamps `User.currencyChosenAt` with the server's clock, as it does for any request that sets `defaultCurrency`: a Settings save that changes the currency (which is when `profileChanges` sends it) is an answer too, USD included. So the stamp isn't a setting and stays out of `ProfileSettings`, and the form never sends it. It's written with `$min` in the route's one write, so the earliest answer stands and none can clear it, which is why the field has no default: absent until answered, never null, which `$min` would keep. The session carries it only as the boolean `currencyChosen`. Lists keep the currency they have: `Wishlist.currency` keeps its schema default, so a list that never stored one stays on USD.
- **An occasion's date is a calendar date, not a timestamp.** `Wishlist.occasion.date` is a `YYYY-MM-DD` string with no time zone, and "today" is the viewer's local date, so a countdown is only worked out in the browser: read the date with `useLocalToday` (`lib/hooks/useLocalToday.ts`), which is `null` in a server render and in the render that hydrates it, so a server whose date differs can't cause a hydration mismatch. Do the date arithmetic with `lib/utils/occasion.ts` (`nextOccurrence`, `daysUntil`, `formatOccasionLabel`, `occasionSortKey`), never by parsing it into a `Date` or with `toISOString()` (that's the UTC date). **A yearly occasion stores no real year**: only its day and month matter, so `occasionSchema` replaces whatever year it's sent with (a birth year, say) with the placeholder leap year `YEARLY_PLACEHOLDER_YEAR` (2000, so Feb 29 stays valid; `normalizeOccasionDate`), and the model refuses a yearly one on any other year. Never show that placeholder: a yearly occasion is shown by its next occurrence, and the settings form asks it for a day and month only. A one-off keeps its real year, and isn't refused once it's past. An occasion goes to whoever can see its list, and never decides who that is.
- Prefer the shared `Select`, `Menu`, `ConfirmDialog`, `BaseModal`, `Skeleton` components over bespoke ones, and `Cover` for any list or item image (it shows the gradient placeholder when the image is missing or fails to load). When a page's layout changes, **update its skeleton to match**. Every dialog (`ConfirmDialog`, `BaseModal`, `CreateWishlistModal`, `FollowListModal`, `ImageCropModal`) manages keyboard focus through `useFocusTrap` (`lib/hooks/useFocusTrap.ts`): focus moves in on open (Cancel, the create form's name field, or else the close button unless the content has an `autoFocus`), Tab stays inside the topmost of them that's open, even one rendered inside another's container (the crop dialog in an item form), and focus goes back to the opener on close. While a dialog's form is busy (the hook's `busy` option: `BaseModal`'s `isSubmitting`, the create form's, a running crop), focus is held on its panel instead of dropping to `<body>` with the disabled control, and goes back to that control, if it can take focus again, when that ends with the dialog still open. A trap only counts the Tab stops inside its dialog, so a popup a control portals out of it (the `Select` menu, on `<body>`) keeps focus on that control instead of having stops of its own. `Select` is a WAI-ARIA select-only combobox (a test finds its trigger with `getByRole('combobox', { name })`, not as a button): the trigger is its one Tab stop, on a page or in a dialog, and keeps focus while the menu is open. Enter, Space or an arrow key opens the menu on the selected option, the arrow keys, Home, End and type-ahead move the active option through `aria-activedescendant`, Enter or Space picks it, and Escape or Tab closes the menu. The open menu's keys stop at the trigger, so its Escape doesn't also close the dialog around it. A new overlay uses the same hook, and a new portalled popup keeps focus on its control the same way.
- **Confirmations never say a reservation goes when it stays.** Leaving, removing someone and moving an item to draft free items but keep the reservations, and deleting a list keeps them too (see the invariants), so no copy says a booking is removed, cancelled or deleted by them. The copy for leaving, removing and deleting lives in `lib/utils/confirmationCopy.ts`, with the gifter's own toasts after accepting an owner invite and after leaving, which add the count the API answers with through `releasedGiftsNote`: after an accept, `cancelledReservations` (the reservations that go from their Reserved page, which can be more than the items it freed), and after a leave, `unbookedItemsCount`. Only the gifter's own copy says what of theirs is kept, and only it carries a count: the leaving member's comes from the items already on their page. Copy an owner reads may say what happens to a reservation in general ("if someone reserved it"), never whether anyone did or how many. A danger `ConfirmDialog` that deletes nothing passes its own `icon` (`logout` for leaving, `user-minus` for removing someone) instead of the trash can, and these dialogs' titles are sentence case.
- **A menu of actions is the shared `Menu`** (`components/Menu.tsx`, a WAI-ARIA menu button: a test finds its trigger with `getByRole('button', { name })` and its items as `menuitem`s; the header's account menu predates it, WIS-220). It renders in place, not portalled, so focus moves into it: Enter, Space (on its keyup, or Firefox would click the item focus lands on) or ArrowDown opens it on the first item, ArrowUp on the last, and a pointer opens it with the menu itself focused. The arrow keys (wrapping), Home, End and a typed letter move between items, and Escape, Tab, a click outside or focus leaving closes it, Escape and Tab with focus back on the trigger. Picking an item puts focus back on the trigger before its action runs, so a dialog the action opens returns focus there when it closes, and focus never strands on `<body>`: an item that goes away under it (a poll) leaves it on the menu, and a menu that closes with it lost puts it on the trigger. A held item (`disabled`) is `aria-disabled`: still in the arrow keys, but picking it does nothing. An item card (`WishlistItem`) keeps its actions to one row of that height: one labelled primary action by role and state (a member's Book / Unbook / a disabled Booked, an owner's Edit, or Publish on a draft, Review on a proposal, the proposer's Edit, else the product link as View item), the product link as a square icon button when it isn't the primary (a "No link provided" marker in its place when there's none), and a "More actions" `Menu` with the rest (an owner's Mark as completed / Mark as available, Move to draft, Edit on a draft, and anyone's Save to my list), left out when it would be empty. While the card's update runs, its status changes (Book, Unbook, Publish, and the menu's Mark as… and Move to draft) are held with `aria-disabled`, so focus on them stays put; Edit, Review and Save to my list stay available, as they always were. A new card action goes into that menu unless it becomes the primary for some role.
- Async UI mutations should be **optimistic** and resilient to the 5s polling on the wishlist page (see `handleUpdateItem`): update locally, merge the server response for the single item, and don't let a stale in-flight poll overwrite fresher local state. Item updates all go through `handleUpdateItem` → `updateItemOptimistically` (`lib/utils/itemListMerge.ts`), which on failure undoes the change at once (the fields it changed go back, unless something else has changed them since) and only then reconciles with a read: that read can be dropped or fail, and a failed read keeps the list. Every item mutation's request goes through the page's `mutations.track` (`createMutationTracker` in `lib/utils/itemListMerge.ts`), which drops any poll that lands while one is in flight or read across one. So each of those requests is also bounded by `withRequestTimeout` (`lib/utils/requestTimeout.ts`): one that hasn't answered within `ITEM_REQUEST_TIMEOUT_MS` is aborted and handled like any other failure, instead of holding off the polls until the browser gives up on it. A read is judged by when its request was sent, not when it was asked for (concurrent reads share one request, so `useFetchItems` takes `mutations.stamp` and reports the shared request's `sentAt`), and a stale read is followed by a fresh one as soon as no mutation is in flight (`mutations.rereadWhenIdle`); a stale non-silent read (the first load) still lands first.
- A list whose cards each have their own action (Invitations, Booked) tracks the cards in flight with `useBusyIds` (`lib/hooks/useBusyIds.ts`): wrap the action in `run(id, fn)` and disable the card's buttons on `busy(id)`. Each card is freed only when its own request settles, and `run` ignores a second call for a card that's already in flight, so don't rely on `disabled` alone. The Booked page also reads its lists again (on a return to the tab, and after a 404), and merges each read into its copy with `mergeRefreshedList` (`lib/utils/listRefresh.ts`) instead of replacing it: a `ListChangeLog` records every entry its actions put on or took off, so a read that predates one can't undo it, and `held: running` leaves a card whose action is in flight as it is.
- **The wishlist settings form sends only what the owner changed.** Co-owners can edit one list's settings at the same time, and the form is filled when the page loads, so a save sends only the fields that differ from the list as the form was last filled (`settingsChanges`, `lib/utils/wishlistSettings.ts`). A field sent regardless would write back the value the form loaded over a co-owner's change, e.g. reopening a list they just made private. Each read of the list (a reload, the save's answer) refills every field the owner isn't editing (`rebaseSettingsForm`), so the next save diffs against the list as it is then. A new setting goes into `WishlistSettings` so it gets the same treatment. **The account settings page works the same way** (`profileChanges` / `rebaseProfileForm`, `lib/utils/profileSettings.ts`), since one account can have it open in two tabs: a save sends only what changed, each privacy setting on its own, and `PATCH /api/users/me` writes each privacy setting it's sent by its dotted path (`privacy.profileVisibility`), never the whole `privacy` object rebuilt from its read, which would make a profile just set to friends-only public again. A new account setting goes into `ProfileSettings`.
- **The item edit form sends only what the owner changed, too.** `EditItemModal` is filled from the item when it opens, and a co-owner may save the same item meanwhile, so a save sends only the content fields that differ from the form as it was last filled (`itemChanges`, `lib/utils/itemForm.ts`, which `ItemForm` hands its `onSubmit` along with the full payload), and closes without a request when nothing did. The price (amount and currency) is one field, and the status is never part of an edit. Above all, an image the owner didn't touch stays out: sent back over a co-owner's replacement it would restore an image that replacement has already freed and free theirs, or be refused as someone else's upload. A new content field goes into `ItemContent` so it gets the same treatment. (`ReviewItemModal` still sends every field; WIS-199 tracks it.)
- TypeScript is `strict`. Keep it green.
- **A count agrees with its noun**: "1 item", "2 items". Write a count and what it counts with `plural(n, 'item')` from `lib/utils/plural.ts`, or `pluralNoun` when the number is set apart from the noun (in bold, say), never with a plural of your own after the number or a ternary. An irregular plural goes into the helper's table, or is passed to it.
- **Accounts are created on the first verified sign-in**, by the adapter's `createUser` (`createUserAccount` in `lib/utils/userAccount.ts`, wired up in `lib/authAdapter.ts`), never in the `signIn` callback, which also runs when a magic link is merely requested. Auth.js only sends a sign-in to `pages.newUser` (`/welcome`, the offer to replace the generated username) when its adapter created the account during that sign-in, so an account created anywhere earlier silently skips the welcome step for everyone. That branch also doesn't end the session the browser was signed in with as someone else (the existing-user branch does), so `events.signIn` does it for a new account, once its own session exists (`endPreviousSession`, `lib/utils/previousSession.ts`, best-effort). `/welcome` continues to its `callbackUrl` only through `safeCallbackPath` (`lib/utils/callbackUrl.ts`), which drops anything off-site. So does the sign-in page for a visitor who's already signed in (never to an `/auth` page, which would loop), so a link with sign-in in front of it doesn't ask them for a magic link. A page that needs a session sends a signed-out visitor to `signInPath('<its own path>')` with `router.replace`, never home, so they come back to it after signing in. Such a page's path goes into `AUTH_ONLY_PATHS` (`signInPath` takes nothing else), which is also how the header's Sign out knows to go home from it instead of reloading it onto the sign-in form; signing out anywhere else stays on the page. A link we send someone (the invite email) points at the page itself, not at sign-in.
- **The session callback returns an explicit allowlist, never the object Auth.js passes in.** With database sessions that object is `{ ...sessionRow, user: userRow }`, so returning it, or anything spread from it, puts the raw session token into `GET /api/auth/session`, where any script on the page can read what the httpOnly cookie hides, along with the user's whole row. `auth()` returns the same result on the server. The shape is built by `sessionPayload` (`lib/utils/sessionPayload.ts`); add a field to `SESSION_USER_FIELDS` only together with whatever reads it, since tests pin the exact shape. The callback builds the session from the user row Auth.js's adapter read for that check, with no read of its own (one would cost every `auth()` a round trip), except to backfill a username into a legacy account that has none. `update()` (settings, welcome) is just another check, so the row is read afresh and whatever the client sends is ignored.
- **sharp's native library has to be shipped by hand.** Next's output file tracing copies sharp's `.node` binding into a route's bundle but not the libvips shared library it links (`@img/sharp-libvips-<platform>/lib/libvips-cpp.*`), so on Vercel the route crashes on its first `import('sharp')` with `ERR_DLOPEN_FAILED` (WIS-156 took sign-in and uploads down). `outputFileTracingIncludes` in `next.config.js` ships libvips with what runs sharp: `/api/upload` and every share card (`opengraph-image`: next/og rasterizes with sharp whenever it can load it, and a list's or profile's card converts its photo with it). `npm run check:trace` (in CI, after the build) fails if any route ships the binding without it, if one of those ships no binding, or if NextAuth's route ships sharp at all. **Sending an email needs no sharp**: its logo is a PNG pre-rendered from `app/icon.svg` (`lib/emailLogo.ts`, by `npm run generate:email-logo`; `test/unit/emailLogo.test.ts` fails when the two drift), so sign-in (NextAuth's route, the sign-in page's server action) never loads sharp. Keep it that way: `test/api/signInWithoutSharp.test.ts` sends a magic link with a sharp that can't load, since the sign-in page's trace can't show it (see below). Pages aren't checked: every page's trace carries the binding, because Next imports the share cards' modules into each page for their metadata (`alt`, `size`, `contentType`), but a page never draws a card, so it never loads sharp. A route or page that does run sharp goes into `outputFileTracingIncludes` and check:trace's `RUNS_SHARP`. (On macOS, Turbopack traces libvips by itself, so a missing include only shows on Linux, where CI and Vercel build.) Outside `app/api/upload`, load sharp lazily (`await import('sharp')`) inside the function that needs it, never at the top of a module many routes import, so a sharp problem degrades that one feature (e.g. a card's photo) instead of the whole route.
- **A link preview shows only what a signed-out visitor could see, and is dropped when that changes.** A messenger fetches a shared link's metadata (`generateMetadata` in `app/wishlists/[id]/layout.tsx` and `app/users/[username]/layout.tsx`) and its share card (`opengraph-image.tsx`, built in `lib/og/`) signed out, shows them to everyone in the chat, and keeps its own copy that nothing can take back. Both read through `lib/og/data.ts`: a list is named (with its banner, primary owner and item count) only when `getWishlistViewAccess(list, null)` admits it, and any other list is `hidden`, answered exactly like a list that doesn't exist (same card, same headers). A profile shows its username and avatar, and its bio unless it's friends-only. A card's photo is fetched only from our own store (`isOwnBlob`: a pasted URL fetched by the server would let anyone aim it at an address of their choosing), capped in size and time, and converted with sharp (lazily), since next/og can't draw WebP; the card itself goes out as a JPEG (`renderCardImage`), since a PNG of a photo runs to megabytes and WhatsApp drops a preview image much over 300 KB. Bots get the page only once its metadata resolves, so every read here, and drawing the card, is time-boxed (`METADATA_BUDGET_MS`, `DATA_BUDGET_MS`, `PHOTO_BUDGET_MS`, `RENDER_BUDGET_MS`) and falls back to the generic answer, and `htmlLimitedBots` (`next.config.js`) is Next's own list plus the preview bots it lacks: keep Next's list in it, since the option replaces it. Only a card that showed real data, still current once drawn, is cached, and only on Vercel's CDN: a day, tagged `og-wishlist-<id>` and `og-user-<primary owner>` (a profile: `og-user-<id>`). A generic or fallback card is `no-store`. So a write that changes anything a card shows calls `purgeShareCards` (`lib/og/purge.ts`) once it has landed: a list's name, slug, visibility, archived flag or banner (`PATCH /api/wishlists/[id]`), its delete, an owner removed, demoted or leaving (`removeWishlistOwner`: it may have been the primary owner; adding an owner appends, so it never changes who that is), an item moving in or out of the count a list's card shows (added, deleted, published, drafted or approved; `isCountedOnShareCard`), and a user's username, bio, avatar or profile visibility (`PATCH /api/users/me`, compared with what its write replaced, `returnDocument: 'before'`, not with its earlier read: a value it's sent may be one the profile already has, and another tab's save can land in between). The purge deletes, never invalidates (a stale card is served once more, which would name a list just made private), is best-effort, and logs no ids. A new field on a card needs the same purge on every write of it.
- **Uploads are sanitized and owned.** Every image is re-encoded with `sharp` on upload (`app/api/upload`), which strips EXIF/metadata and bakes in orientation. **An upload has to be the type it declares**, because sharp picks its decoder from the bytes, never from `file.type`: the route answers a mismatch with the same 400 as an unsupported type, first when the leading bytes lack the declared type's signature (checked before sharp reads anything, so only the declared type's loader ever gets the file), then when the format `metadata()` reports isn't the declared type's (an AVIF must be `heif` with AV1 compression, since HEIC shares libheif's loader), before any pixels are decoded. **librsvg never parses an upload**: also before sharp reads anything, whatever the declared type, the route refuses with that same 400 any file libvips' own SVG sniff would claim (`sniffsAsSvg`, which mirrors libvips' `svgload` `is_a`: an `<svg`, in any case, before the first byte that isn't valid UTF-8, or gzip's magic), since a GIF's or WebP's signature can start such a file. A test checks it against the bundled libvips' own sniff, so a libvips that sniffs differently fails it. These checks live in `lib/utils/uploadImageFormat.ts`. Loading the route also blocks, process-wide, every libvips loader except JPEG's, PNG's, WebP's, GIF's and HEIF's, plus SVG's (`UPLOAD_ROUTE_LOADERS`), which has to stay because next/og rasterizes every share card from an SVG with sharp: blocking it would break every card wherever the upload route has loaded. Any other sharp code that needs a loader outside that list has to add it there, or it fails wherever the upload route has loaded. Blobs live under `uploads/<userId>/` and count against a per-user quota. When an image field (`Item.imageUrl`, `User.image`, `Wishlist.bannerUrl`) is replaced or its record deleted, free the old blob with the helpers in `lib/utils/blob.ts` — but **only ever delete our own blobs** (`isOwnBlob`, which matches our exact store host, derived from `BLOB_READ_WRITE_TOKEN`); a user-pasted external image URL must never be deleted. Free the image the write actually replaced, never the one the request read before it: two owners replacing one image at once both read the same one, so freeing that read frees it twice and orphans the image the first put in its place. So an edit that replaces or clears an image takes the old value from its own write (`findOneAndUpdate` with `returnDocument: 'before'`) and hands it to `freeReplacedImage`, and deleting an item frees the image of the document `findOneAndDelete` returned. An edit that sends the image the field already holds (`isSameImage`: the item review form always sends it) doesn't write it at all: written back over a replacement that landed after the read, it would restore an image that replacement has already freed. Because whatever a record holds gets freed, **you may only attach blobs from your own `uploads/<yourId>/` folder**: every route that writes one of those fields checks `canAttachImage(next, actorId, current)` and returns 400 `FOREIGN_IMAGE_ERROR` otherwise. Keeping the value already on the record is allowed (a co-owner's upload on an item or banner, a proposer's image on an approved proposal), and external URLs are always allowed. Two items never share a blob, since freeing one would break the other: saving a copy of an item ("Save to my list", `sourceItemId` on `POST /api/wishlists/[id]/items`) copies the source's blob into the caller's own folder with `copyBlobToUploads`, against their quota, and saves without the image (with a `notice` in the reply) when it doesn't fit. The one other kind of blob is a **snapshot** under `snapshots/`: once a booking's reservation is written, `snapshotReservationImage` copies the item's image there and points the reservation at the copy (best-effort: on failure it keeps the item's URL), so the gifter's `Reservation` / `GiftLog` image survives the owner deleting the item or replacing its image. Snapshots count against nobody's quota (a booking-blind owner's must never move because someone booked) and fail `canAttachImage`. Free them only through `lib/utils/reservationSnapshots.ts`: `deleteReservations` for any reservation that ends without a gift, `releaseSnapshots` when a rebooking replaces one or a gift-log entry is deleted. Marking the gift takes the reservation in one atomic delete and hands its snapshot to the `GiftLog`, which keeps it; a snapshot has one holder at a time, so hand it on atomically or a concurrent dismiss frees what the log shows. Never free a reservation's or gift log's image with `deleteOwnBlob`: an older one (or one whose copy failed) holds the item's own blob.
- **Schema migrations are HTTP endpoints** under `app/api/migrations/<name>/route.ts`, built with `createMigration` (`lib/utils/migration.ts`) and gated on the `X-Migration-Secret` header. Run with `curl -X POST -H "X-Migration-Secret: $MIGRATION_SECRET" <host>/api/migrations/<name>`. There are none in the tree right now — the co-ownership set and `dedupe-pending-invites` were applied to every environment and deleted (see git history). When you add one:
  - Make it **idempotent**, so re-running is free and a partial run can be finished by running it again.
  - Decide its **deploy ordering** and say so in the docstring. An _additive_ migration (only writes new fields) is safe to run before the deploy, because the live old code still reads what it needs. One that removes or moves data the old code depends on must run **after**, or it breaks the running deployment.
  - If the reading code needs a fallback for the un-migrated shape, gate that fallback on the new field being absent, and delete it in a follow-up once the migration has run everywhere. Don't leave fallbacks behind — they quietly become unreachable code that still has to be reasoned about.
  - A new **unique index** on a collection that may already hold duplicates needs one that dedupes and then builds the index itself (`Model.createIndexes()`). Mongoose's `autoIndex` is on (`lib/mongodb.ts` doesn't change it) but fails such a build silently — the error only reaches the model's `'index'` event — so without the migration the index just never appears.

- **Rate limiting goes through `enforce()` / `checkRateLimit()` in `lib/rateLimit.ts`** — never hand-roll an in-memory counter (Vercel's per-request instances don't share it). Add a new surface by adding a `SPECS` entry (tokens/window/policy/keyKind) and calling `enforce('<name>', key)` right after the auth/access check, returning its response if non-null. Build keys only with the helpers: key **authed** writes on `userKey(session.user.id)`; key **public** reads on `ipKey(request.headers)`; key the sign-in email path on **both** `emailKey(email)` and `ipKey`. A key's brand must match its entry's `keyKind` (a type error otherwise, so pass the limiter name as a literal), because every block logs one JSON line `{"event":"rate_limited","name","keyKind"}` for tuning `SPECS`, and that line must never carry the key itself (it's an email, IP or user id); the same goes for any other log line in the limiter. Choose `fail-open` for user-facing reads/writes and `fail-closed` for cost-bearing email sends. The policy covers the store **timing out** as well as throwing: on a slow Redis `@upstash/ratelimit` doesn't throw but resolves `{ success: true, reason: 'timeout' }` after `STORE_TIMEOUT_MS`, which `run()` treats as a store error — so never act on the SDK's `success` without going through `run()`. Limiting is **disabled** when neither `UPSTASH_REDIS_REST_URL`/`_TOKEN` nor their `KV_REST_API_URL`/`_TOKEN` fallbacks are set (CI/tests) — tests inject a fake via `__setRateLimiters`, they don't need Redis. A `.env` pulled from Vercel carries the `KV_*` pair, so local dev _does_ rate-limit against that store.
- **A magic link is only sent by the sign-in form's server action** (`requestMagicLink`, `app/auth/signin/actions.ts`). It checks the Cloudflare Turnstile token with `verifyTurnstileToken` (`lib/turnstile.ts`) before anything else, then calls Auth.js's server-side `signIn` inside `asVerifiedSignIn` (`lib/signInEmail.ts`). Auth.js's own `POST /api/auth/signin/<provider>` answers 403 (`isMagicLinkSignInPath`), and a request that didn't start inside `asVerifiedSignIn` is refused by the `signIn` callback (`email.verificationRequest`) and by `sendVerificationRequest`, so any new way to send a sign-in link goes through that action, never around it. Turnstile is on only when both `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` are set (`getTurnstileKeys`), and `lib/env.ts` refuses one without the other. The sign-in page reads them per request and hands the site key to the form, so the widget and the check never disagree. Only the token can fail the check closed, a missing one included. That one is still put to Cloudflare (as an empty response), because the form sends none when Turnstile's script couldn't load or run, which is what a Cloudflare outage looks like in the browser. When Cloudflare gives no verdict (unreachable, no answer within `TURNSTILE_VERIFY_TIMEOUT_MS`, a 5xx, `internal-error`, a secret it rejects), the check fails open and logs `turnstile_unavailable`, and the fail-closed sign-in limiters stay the backstop. Its log lines carry no token, IP or email.
- **Email HTML escapes every user-controlled value.** `getEmailTemplate` (`lib/email.ts`) escapes its plain-text fields (title, greeting, button text, URLs). `contentHtml` / `footerHtml` are raw HTML, so pass every value you interpolate into them (a wishlist name, a display name, an address) through `escapeHtml`: a wishlist name is free text, and unescaped it can put a live link in a mail sent from our domain. Button and fallback URLs must be links we build, never a user-supplied URL, because escaping doesn't vet the scheme. Plain-text parts and subjects take the raw value, so free text that goes into them must be one line: the wishlist name's schema (`lib/validations.ts`) refuses line breaks and other control characters, and any new free-text field you put in an email needs the same check.
- **Server logs carry no personal data**: anyone with project access reads them. Never log a user's email or user id, anything that says who is on, left or booked on which list, or a count of someone's bookings; a success path needs no log line. Log the event and the error, but reduce an error that quotes its input to its kind (a MongoDB duplicate-key error carries the clashing value, e.g. an email). A record id (invite, wishlist) may stay in a failure line that needs it for repair by hand, never next to a user id, and a blob URL is logged with its `uploads/<userId>/` folder masked. `test/unit/noEmailsInLogs.test.ts` catches an email-named value in a `console.*` call; the `smtp` and rate-limiter rules above still apply.
- **Never print, commit, or expose secrets** (`.env*`). Never read or use production credentials (`.env.prod`, `.env.staging`), and only perform authorized DB operations.

## Keep docs current

When a change affects how the project is set up, run, or structured, update the docs in the **same** change — stale docs are worse than none:

- New/changed/removed **env var** → update `README.md` and `.env.example`.
- New/removed **npm script**, dependency, or tech-stack change → update `README.md`.
- New user-facing **feature** or removed one → update the README feature list.
- New **convention, invariant, or workflow** for contributors → update this `AGENTS.md`.
- **Deferred ideas and follow-ups** go to Linear (Backlog), not into a file in the repo — design notes for a large feature belong in its Linear project description.
