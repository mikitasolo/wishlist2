# AGENTS.md

Working instructions for AI agents (and humans) contributing to this repo. Keep this file current when conventions change.

## Project

A wishlist app: **Next.js 16 (App Router), React 19, TypeScript, MongoDB/Mongoose, NextAuth v5 / Auth.js (database sessions), Tailwind v4, Vercel Blob**. Package manager is **npm**. Path alias `@/*` maps to the repo root.

## Commands

```bash
npm ci               # install deps (Conductor's setup script runs this for you)
npm run dev          # local dev server — in Conductor: npm run dev -- --port $CONDUCTOR_PORT
npm run lint         # eslint — must pass before done
npm run format:check # prettier --check — must pass before done (npm run format fixes it)
npx tsc --noEmit     # typecheck — must pass before done
npm run test:cov     # full Vitest suite (unit + component + API) + the coverage floor in vitest.config.mts — must pass before done
npm run build        # production build — must pass before done
npm run check:trace  # after a build: sharp's native libvips ships with every route that ships sharp (the upload route, share cards), and NextAuth's route ships none (CI runs it)
npm run smoke:deploy -- <url>  # read-only GET smoke of a deployed host (auth + upload routes start, a share card draws); safe on staging
npm run generate:email-logo    # re-render the email logo (lib/emailLogo.ts) from app/icon.svg; rerun when the logo changes
npm run test:e2e     # Playwright end-to-end suite
npm run test:watch   # watch mode
npm test             # the same suite without coverage
npm run release:preview  # list commits remote staging is ahead of remote main (dry run)
npm run release          # promote: fast-forward remote main to remote staging — operator only
```

## How work flows

Tasks live in **Linear** — workspace `mikitasolo`, team **Wishlist**, issue keys `WIS-<n>`. Each issue is worked in its own **Conductor** workspace (a git worktree + branch cut from `staging`), usually by an AI agent. The human is the **operator**: they write and clarify requirements, review, merge, and release.

### Branches

- **`staging`** is the default and integration branch. Every change reaches it through a **pull request**, which the operator **squash-merges**. CI (`ci.yml`, `e2e.yml`) runs on every PR; `audit.yml` runs only on a PR that changes `package.json` or `package-lock.json`, plus daily on `staging` and on demand (see the `overrides` item under Conventions). **Vercel builds only `staging` and `main`** (`git.deploymentEnabled` in `vercel.json`): a PR branch gets no preview deployment, because on the Hobby plan a busy day of PR pushes used up the daily deployment cap and left `staging` itself undeployed. Vercel matches those keys as minimatch globs, where `*` stops at a `/`, so the catch-all is `"**"`: with `"*"` every `nikitasolo1134/wis-…` branch still deployed (WIS-185). `test/unit/vercelConfig.test.ts` pins which branch names build. CI is the PR's check; a change's first real Vercel build is its `staging` deploy, so smoke `staging` after a merge that touches the build, env or runtime setup.
- **`main` is production** (Vercel deploys on push). It only ever moves by **fast-forwarding to `staging`** (`npm run release`, i.e. `git push origin origin/staging:main`) — never commit to `main`, never open a PR into it. This keeps `main` a strict prefix of `staging` (identical hashes, no divergence).
- **A push to `main` is a release.** `.github/workflows/release-notify.yml` posts the changelog to a Telegram channel (built from the commit subjects in the pushed range by `.github/scripts/telegram-release-notes.py`) and moves the Linear issues those commits close from **On Staging** to **Done** (`.github/scripts/linear-mark-released.py`). Secrets: `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` / `LINEAR_API_KEY`; without them each job prints a preview and changes nothing.

### Issue statuses

| Status      | Meaning                                         | Moved by                                    |
| ----------- | ----------------------------------------------- | ------------------------------------------- |
| Backlog     | Idea, or not specified well enough to build yet | operator                                    |
| Todo        | Spec is ready — an agent can take it            | operator                                    |
| In Progress | Being worked in a workspace                     | the agent, when it starts                   |
| In Review   | PR is open                                      | Linear's GitHub integration                 |
| On Staging  | Squash-merged into `staging`, not yet released  | Linear's GitHub integration                 |

| Canceled    | Won't do                                        | operator                                    |

Labels: one **Type** (Feature / Bug / Improvement / Tech debt — maps to the commit prefix) and one **Area** per issue. Large features are Linear **projects**; their design notes and open questions live in the project description, so read it before starting an issue inside one.

### Agent lifecycle for an issue

1. **Read the issue** (`WIS-<n>`) through the Linear MCP server — description, comments, and the parent project's description if it has one. If the acceptance criteria are missing or ambiguous, especially anywhere near the domain invariants below, **ask the operator before writing code**. Don't guess at product decisions.
2. **Move the issue to In Progress.**
3. **Stay in your workspace branch.** Conductor created it from `staging`; don't rename it, and never check out, commit to, or push `staging` or `main`.
4. **Implement with tests** (see Testing policy). Stay in scope: an unrelated bug or idea you notice becomes a **new Linear issue in Backlog** (link it from the PR), not part of this change.
5. **Verify**: everything marked "must pass before done" under Commands passes locally, plus `npm run test:e2e` if you touched a flow the E2E smoke tests cover.
6. **Review your own diff** (`git diff origin/staging...`) as a skeptical reviewer would — correctness, the domain invariants, missing tests, leftover debug code, docs the change makes stale — and fix what you find.
7. **Commit, push your branch, and open a PR into `staging`** (`gh pr create --base staging`), following the rules below.
8. **Get CI green** (`gh pr checks --watch`) and fix failures. Branch protection isn't available on the free GitHub plan, so nothing else stops a red PR from being merged.
9. **Hand off**: reply with the PR link, what changed, how you verified it, and anything the operator has to do by hand (env vars, migrations, dashboard config).

**Operator-only** — never do these as an agent: merge a PR, run `npm run release`, run a migration against a deployed host, change env vars or secrets in Vercel/GitHub, or push to any branch other than your own.

### Pull requests & commit messages

**PR titles are published.** A PR is squash-merged, so its title becomes the commit subject on `staging`, and every subject in a release goes verbatim into the Telegram changelog. The title is release-note copy, not a note to yourself:

- **Conventional-commit prefix**, which the changelog groups by: `feat:` `fix:` `perf:` `refactor:` `docs:` `test:` `build:` `ci:` `chore:`. Anything unprefixed lands in a catch-all "Other" section — avoid it.
- **Imperative, specific subject** that stands alone. A reader in the channel sees only the subject, with no diff and no body: `fix: release a member's bookings when they're made an owner`, not `fix: bug` or `fix: address review comments`.
- **No issue ID in the title** — the channel's readers don't have Linear. Put `Closes WIS-<n>` in the **body**: that links the PR to the issue and drives its status. Use `Part of WIS-<n>` for a PR that doesn't finish the issue.
- **The body becomes the squash commit's message**, so it explains _why_, plus anything a future reader would otherwise have to reconstruct: the invariant being protected, the failure mode being closed, migrations the change requires and their ordering, how it was tested. Follow `.github/pull_request_template.md`.
- **One issue, one PR, one coherent change.** "Various fixes" is one useless changelog line covering several things worth naming. Commits inside the branch can be as granular as you like — they're squashed away — but still use the conventional prefixes.

### Parallel workspaces

Several agents run at once, each in its own worktree. Don't assume anything is exclusive to you:

- **Ports**: dev runs on `$CONDUCTOR_PORT` (the Conductor run script passes it); E2E derives its port from `CONDUCTOR_PORT` too (`playwright.config.ts`). Never hard-code 3000/3100.
- **`next dev` leaves `AGENTS.md` alone**: Next 16.3 appends a managed "nextjs-agent-rules" block to it whenever it detects an AI coding agent, which left every workspace with an uncommitted change. `agentRules: false` in `next.config.js` turns that off; keep it.
- **Conflicts**: other PRs touch `README.md` / `AGENTS.md` too. When yours conflicts, rebase onto `origin/staging` and force-push **your own branch** with `--force-with-lease`; don't merge `staging` into it.
- **Local dev data**: workspaces get the repo root's `.env` / `.env.local` copied in (`.conductor/settings.toml`); `.env.prod` / `.env.staging` deliberately aren't. The dev MongoDB is shared by every workspace — don't wipe or bulk-edit it. Prefer the test suites (in-memory Mongo, mocked email) over poking the dev server. When you do run it, use `EMAIL_TRANSPORT=console`: every email (the magic link included) is printed to the dev-server log instead of sent, so no SMTP credentials are needed and no real mail goes out. Only that transport ever prints an email's recipient or link; the `smtp` path in `lib/email.ts` must never log them, not even in a send error. A printed magic link is a working sign-in credential, so `lib/env.ts` allows `console` only where `VERCEL_ENV` is unset (local dev, CI, E2E) or `development`, and refuses it on Vercel Preview and Production.

## Testing policy (required)

**Add or update tests for every change that touches logic — no exceptions for "small" fixes.** The booking flow, currency conversion, privacy gating, and invite/gift lifecycle are exactly the kinds of things that broke before and must stay covered.

- **New pure logic** (`lib/utils/**`, Zod schemas in `lib/validations.ts`) → a unit test.
- **New/changed interactive component behavior** (conditional rendering, state, optimistic updates) → a component test. Skip purely presentational markup.
- **New/changed API route with authorization or business rules** → an API test (in-memory Mongo + mocked session).
- **Every bug you fix** → a regression test tagged with a `// regression:` comment citing the cause, so it can't silently come back.
- Before considering work done: everything marked "must pass before done" under Commands passes — the same checks CI runs.

Chase meaningful coverage of logic/authorization, not a headline line-coverage number.

### Test layout & harness

- `test/unit/**` — pure functions and schemas (node env, no DB).
- `test/components/**` — React Testing Library; **add `// @vitest-environment jsdom`** as the first line.
- `test/api/**` — route handlers against a real in-memory MongoDB. Pattern:
  - `vi.mock('@/lib/mongodb', ...)` → no-op `connectDB` (the shared mongoose connection from `test/db.ts` backs the models).
  - `vi.mock('@/lib/auth', () => ({ auth: vi.fn() }))`, then `const session = vi.mocked(auth)` to control the session (NextAuth v5 — routes call `auth()`, not `getServerSession`).
  - Mock `@/lib/email` / `@/lib/utils/currencyRates` when a route would otherwise send mail or hit the rates API.
  - `connectTestDB` / `disconnectTestDB` / `clearTestDB` from `test/db.ts` in `beforeAll` / `afterAll` / `beforeEach`.
- **Mock lifecycle (Vitest 5).** Every mock's call history is cleared before each test (`clearMocks` is on by default and runs before `beforeEach`), but its implementation isn't: `vi.restoreAllMocks()` only puts back what `vi.spyOn` replaced, and leaves a `vi.fn()`'s `mockResolvedValue` / `mockImplementation` in place for the next test (Vitest 3 used to reset those too). So a shared `vi.fn()` that tests configure (the mocked `auth`, `sendEmail`, `fetch`) gets a `mockReset()` in `beforeEach`, as the API tests do with `session.mockReset()`. `vi.mock` / `vi.hoisted` must sit at the top level of the file (nested, they throw), and an un-awaited `expect(…).resolves` / `.rejects` fails the test.
- Vitest config injects dummy env vars (see `vitest.config.mts`) so import-time env reads don't throw. Vitest only picks up `test/**/*.test.{ts,tsx}`; Playwright specs live in `e2e/**`.
- `e2e/**` — Playwright (`npm run test:e2e`). `e2e/global-setup.ts` starts an ephemeral MongoDB, seeds a user who owns the `e2e-birthday` list and is a member of another user's `e2e-friend` list (so specs can take either side), plus a database session (writing a `authjs.session-token` storageState so the `authed` project is logged in without magic-link), and unused magic-link tokens (`e2e/magicLinks.ts`: three for emails with no account yet, one for the friend, plus a session for the friend) so a spec can sign up or sign in through Auth.js's real callback without any email (each link works once), then builds and starts the app; `global-teardown` stops both. Specs are `*.public.spec.ts` (signed-out) or `*.authed.spec.ts` (signed-in). Every spec, a new one included, imports `test` and `expect` from `e2e/fixtures.ts`, never from `@playwright/test` (ESLint refuses it; types may still come from there). Its `test` fails a spec whose pages throw an uncaught error (`pageerror`, an unhandled promise rejection included), which can't be allowed, or log a `console.error` that isn't allowed. A failure the spec provokes on purpose (a request it answers with an error status or aborts, which the browser logs as `Failed to load resource`, and the app's own log line for it) is allowed in that spec with `consoleErrors.allow(failedRequest(/…path…/), /^Error updating item: /)`, matched as narrowly as it can be. A context the spec opens itself (`browser.newContext()`) is only guarded once handed to `consoleErrors.watch`. The suite-wide `ALLOWED_CONSOLE_ERRORS` there is only for an error no spec can avoid, each entry with a comment saying why and which issue tracks it; it's empty today. Keep E2E to a few resilient smoke tests per flow — unit/component/API tests carry the detailed coverage.

## Domain invariants — do not regress

These are correctness/privacy rules the product depends on:

- **A wishlist has exactly two kinds of people: owners and members.** There is no `admin` tier — a manager of someone else's list isn't a relationship the product needs, so anyone trusted to manage a list is a co-owner. Owners live in `Wishlist.owners[]`; members are rows in `WishlistMember`, which carries **no role field**. Membership is existence, not a level.
- **All co-owners are equal.** Identical authority (including deleting the list), the list shows on each of their profiles, and none of them ever sees booking status. Authorize owners only through `isWishlistOwner` / `ownedByFilter` / `primaryOwnerId` from `lib/utils/wishlistOwners.ts`, or `getOwnerAccess` / `isOwnerOfWishlist` from `wishlistAccess.ts` — never by hand-rolling a check on `owners[]`. A list must always keep at least one owner: take an owner off only through `removeWishlistOwner` (`lib/utils/wishlistOwnership.ts`), whose single conditional write refuses the last one and refuses an actor who is no longer an owner, and stop before any side effect unless it returns `'removed'`. An `isLastOwner` check or an owner check on the caller against an earlier read is only a pre-check — on its own it races (two co-owners leaving at once both pass it; so do two owners removing each other), and the schema's non-empty validator doesn't run on `updateOne`. The same goes for the caller of an owner-only write: deleting a list is one `findOneAndDelete`, and editing it (settings and the `featured` pin together) one `findOneAndUpdate`, each filtered on `ownedByFilter(callerId)`, and nothing else is touched unless it matched. Where the writes live on other collections and so can't carry the check (kicking a member, inviting or promoting someone), re-read ownership right before the first change. That only narrows the race to the gap before the next write, so prefer a conditional write whenever the write is on the `Wishlist` itself. A caller who lost ownership mid-request gets the same answer as any non-owner.
- **Members have no management powers.** They browse, propose items, and book gifts. They can't see the members list, drafts, wishlist settings, or publish an item directly. Everything else is owner-only.
- **Owners never see booking status.** For any owner, `booked` folds into `available`; never reveal who booked what.
- **"N items" means a list's published items, on every screen.** That's available, booked and completed, with booked folded in for everyone, so no count anywhere says how much is reserved. Count with `lib/utils/itemCounts.ts` (`isPublishedItem`, `tallyItems`, the formatters), or on the server with `countWishlistItems` (`lib/utils/wishlistItemCounts.ts`), never with a status filter of your own. Drafts and proposals to review are counted only for an owner on an owner surface ("11 items · 2 drafts · 1 to review": the `draftCount` / `proposalCount` that `GET /api/wishlists` puts on your own lists only), so a member never sees a draft or anyone's proposal counted. The share card counts the same set (`isCountedOnShareCard`), so changing the set also changes which writes have to purge it. `test/api/itemCounts.test.ts` checks that every source gives one list the same count. Item totals across your lists leave archived lists out (the dashboard; `/items` unless you ask for them).
- **Becoming an owner requires consent and releases your bookings.** The three ways in are: create the list, accept an `owner` invite (`POST /api/wishlists/[id]/members` by username), or accept a promotion (`POST /api/wishlists/[id]/owners/[userId]`, which issues the same kind of invite — never a silent role write). The `/members` invite honours the invitee's `whoCanInvite`; promotion skips it, so it is only ever issued to an **existing member** (404 for anyone else, identical whether or not the user exists). On accept, `addWishlistOwner` frees the items that person booked **and deletes their reservations** — an owner can't be their own gifter. This is the one place that deletes a reservation on a membership change; leave/remove deliberately keep it (a booking that loses the race to one only ends the reservation it wrote itself: see the next item).
- **A booking must never be left where nobody can release it.** Only the holder can cancel a booking, and owners are booking-blind — so becoming an owner has to free their booked items first, or the item sits claimed forever (invisible to them, hidden from the owners, unbookable by everyone else). Route role transitions through `releaseHoldingsForRole` (`lib/utils/wishlistOwnership.ts`): → owner frees items **and** cancels reservations; → member does nothing (members manage their own bookings). Leave/remove free the items and keep the reservation, so the gifter can still log a gift they went on to give. Demotion and visibility changes need nothing — members retain access at every tier, and only members can book. A booking in flight is the other half: the item route reads the caller as a member at the top of the request, so once a member's booking has written the item and its Reservation, `undoBookingUnlessMember` (`lib/utils/lateBooking.ts`) re-reads their role. If they've since left, been removed or become an owner, or the list was archived, it frees the item and ends the Reservation it wrote (one it overwrote is put back, unless they're now an owner), and the request is refused. That re-check only closes the race because becoming an owner grants the ownership before it releases, and a member's leave or kick frees their bookings again after the membership delete (`releaseLateBookings`). A new way off a list, or into its owners, keeps the same order.
- **Never report a released-booking count to an owner.** "2 items released" tells them how much of the list was reserved. Counts only go back to the gifter themselves (invite accept, leave).
- **Being demoted, removed or kicked tells you, and only you.** A demotion sends the demoted owner a `role_changed` notification (linking to the list), and removing an owner or kicking a member sends a `removed_from_wishlist` one (with no link, since the list may now be hidden from them). Deleting a list notifies nobody: it clears that list's notifications instead, and `createNotification(s)` (`lib/notifications.ts`) takes back one written for a list that's gone by the time it lands, so write a list's notifications only through them. Each goes out only once its write has landed, never for a refused or lost one, and never for leaving. Neither names the owner who did it (`createNotification` drops any actor for both types, as it does for proposals), mentions bookings, or reaches the other owners.
- **Losing ownership clears the per-owner state.** Demote, remove, or leave pulls the user from `owners` **and** from `featuredBy`. Only owners may change ownership, and nobody may change their own role.
- **Leaving a list or losing a role on it cancels your pending invites for it.** Accepting an invite grants the role it names, and it can't just refuse non-members (`owner` invites legitimately go to them), so a leftover one would let the person removed undo it, e.g. a kicked member accepting a pending promotion and coming back as a co-owner. Leave, kick, remove-owner and demote therefore call `cancelPendingInvites` (`lib/utils/wishlistInvites.ts`). An owner write (remove-owner, demote, a co-owner leaving) calls it once the write has landed, never before it and never when `removeWishlistOwner` refused it. (A co-owner's leave that it refused because a demotion has just made them a member goes on as that member's leave, which calls it as below.) A kick or a member leaving calls it both before its membership delete and after it, and answers 404 instead of success when that delete matched nothing. It deletes only that person's _pending_ invites for that list (accepted/declined rows stay) plus their `wishlist_invite` notifications for it, the latter best-effort.
- **An owner taken off the owners loses the invites they sent; one who leaves doesn't.** Remove-owner and demote also call `cancelInvitesSentBy` (`lib/utils/wishlistInvites.ts`) once `removeWishlistOwner` has returned `'removed'`: someone the owners took off mustn't still bring people on (as co-owners, even). It deletes each of that owner's _pending_ invites for the list, paused ones included, in its own conditional delete on the pending row, so it races an accept like an owner's cancel does: an invite the invitee has already claimed stays claimed, and that accept completes. The invitees' `wishlist_invite` notifications go best-effort (`clearCancelledInviteNotifications`, which an owner's cancel uses too). A co-owner who leaves of their own accord keeps theirs: they're the list's, and any owner can cancel them. Because that cleanup reads the invites before deleting them, both invite routes (`POST /members`, `POST /owners/[userId]`) re-check the inviter's ownership once their invite exists (`withdrawUnlessInviterOwns`), and withdraw it and answer as to any non-owner if it's gone. That check can't tell a leave from a removal, so an invite issued while its inviter leaves is withdrawn too. The same goes for an accept that reopens its claim (a failed grant, a list archived under it): the cleanup skipped the invite while it was claimed, so once reopened it's withdrawn if its inviter no longer owns the list, unless the grant had already made the invitee an owner. **`invite_accepted` never reaches a former owner**: it goes to the inviter only while they still own the list (read once the role is granted), and otherwise to every current owner but the invitee (`createNotifications`).
- **An invite is answered by claiming it, before anything is granted.** Accept and decline record the answer in one conditional write on the pending invite, and answer 404 when it matches nothing. Once the answer has landed (an accept's once the role is granted), `recordInviteAnswer` (`lib/notifications.ts`) writes it onto the invitee's own `wishlist_invite` notification and marks that read, best-effort, so it reads "You joined …" or "You declined the invite to …". Notifications carry no invite id, so it picks the row by time: written between the invite and the answer. An owner's cancel, a removal's `cancelPendingInvites` and an owner removal's `cancelInvitesSentBy` are conditional deletes on that same pending row, so exactly one of any of them racing lands. If granting the role then fails, the claim is reopened (back to `pending`), and accepting again finishes the job. A promotion invite carries `promotion: true` (set only by `POST /owners/[userId]`), and accepting it, or any `owner` invite whose invitee is a member, goes through `promoteMemberToOwner` (`lib/utils/wishlistOwnership.ts`). That takes the membership row in one conditional delete before it grants ownership. Kick and leave delete that same row, so a removal and a promotion can't both land. When the row is already gone, nothing is granted and the claimed invite is withdrawn (`withdrawInvite`): a promotion never makes a non-member an owner, whenever they left. A promotion also re-checks the membership once its invite exists, and withdraws the invite with the same 404 if the member has gone (but not if they've already accepted it, which takes the row too). An accept that loses to a list delete grants nothing either. Deleting a list removes the list before its memberships, so joining checks the list _after_ its membership upsert and takes the row back if the list is gone. `addWishlistOwner` / `promoteMemberToOwner` return `null` when their ownership write matched no list, and skip the booking release, which on a deleted list would only destroy reservations the delete keeps on purpose. Either way the claimed invite is withdrawn, and the answer is the 404 `This wishlist no longer exists`.
- **"Featured" is per-owner** (`Wishlist.featuredBy[]`), not per-list: on a co-owned list one owner can pin it to their dashboard without touching anyone else's. API responses fold it to a boolean `featured` for the caller via `serializeWishlist`. On the list's page it's **Pin to my dashboard** in the ⋯ menu of the header (`components/WishlistHeader.tsx`), beside Leave list…, and never in the settings form: it isn't a setting of the list.
- **Never expose user emails to other users.** Invite/notification emails are used server-side only. When someone may have no username, name them to others with `publicDisplayName` (`lib/utils/displayName.ts`: username, then `name`, then "Someone"), never with any part of their email. That goes for defaults too: a username is public, so a generated one (`generateUniqueUsername`, `lib/utils/username.ts`) is a random `user_<8 base36>` handle and the generator takes no input at all, so it can't derive one from the email. (Accounts created before this rule kept the handle they had: nothing renames them.)
- **Invites are registered-users-only** (by username). There is no email-invite path; invites match `invitedUser`.
- **One pending invite per person per list, and an issued invite never hinges on its email.** Issue invites only through `issueWishlistInvite` (`lib/utils/wishlistInvites.ts`). A unique partial index on `WishlistInvite { wishlist, invitedUser }` (`status: 'pending'`) refuses a concurrent duplicate, which is answered as "already pending" with no second email or notification. Partial on purpose: accepted/declined rows are kept, and a declined invitee can be invited again. Once the invite exists its notification is created regardless, and a failed email is caught and logged but doesn't fail the request.
- **Proposals are anonymous to the owner.** Owners never see who proposed an item (`proposedBy` is hidden in the items API), and this extends to notifications: the `proposal` notification carries `actorUsername: null` and renders as "Someone proposed…". Never surface the proposer to the owner anywhere. Owner-facing notifications fan out to **every** owner (`createNotifications`).
- **Gifting is decoupled from the live item.** Booking creates a durable `Reservation` (survives owner status changes and leave/kick). Marking a gift writes a permanent `GiftLog` and deletes the reservation but **does not modify the owner's item**. Owner status changes (`complete`/`draft`/reopen) clear `bookedBy` but must **not** delete reservations. A member's own book and unbook write the item first and their Reservation second, through `writeBookingReservation` + `settleBookingReservation` / `cancelUnbookedReservation` (`lib/utils/bookingReservations.ts`), which re-read the item afterwards. If the same person's book and unbook from two tabs crossed, the Reservation is put back the way the later of the two would have left it: a booking that was released by their own unbook (or by their becoming an owner) deletes the Reservation it just wrote, and an unbook whose item they've booked again writes it back. What keeps a Reservation on purpose still keeps it: an owner's status change, the item's deletion, leave/remove. **The Reserved page releases an active reservation through that same unbook**: its Release sends `PATCH /api/items/[itemId]` (the item id comes from the reservations read), never a path of its own that frees an item, so `cancelUnbookedReservation` settles the Reservation as it does for an unbook from the list. A refused unbook (no longer a member, no longer their booking, the list out of their reach) says so and reads the page again. A card is active only while the item is booked by the gifter (`stillReserved`) on a list they can still open (`listOpen`: `readReservationWishlists` has it, so it's their own access), since the item route refuses everyone else. Any other card needs their confirmation, and only those offer Dismiss (`DELETE /api/reservations/[id]`), which ends just that Reservation and never touches the item. One on a list that only its archiving keeps them from opening (`listArchived`) is frozen (WIS-124): the read gives no live `itemStatus` or `stillReserved` (both `null`), no slug and no occasion, and the card shows only its snapshot, names the list without a link, and says "This list was archived", whatever has happened to the item, until the list is unarchived. It's settled as before, by Mark as given or Dismiss. One still reserved to them on a list they can't open for any other reason (only an owner can release it then) says "This list is no longer available to you", never why, and "No longer reserved to you" is kept for an item that really isn't theirs any more (`reservationNote`, `lib/utils/reservations.ts`). **A gift given stays given on the list**: marking it leaves the item booked by the gifter, so a member's own items read (`GET /api/wishlists/[id]/items`, and their own `PATCH` answer) flags with `givenByMe` each item whose booking they hold and have marked as given: their gift history has the item, and they hold no Reservation for it, since marking a gift ends the booking's Reservation and a later booking of the same item writes a new one (`itemsGivenBy`, `lib/utils/giftHistory.ts`, best-effort), and the card shows "Given by you" in place of Release, with Release… in its menu behind a warning that someone else could then buy it again. It's read only from the viewer's own `GiftLog` for their own bookings, and never computed for, or present in, an owner's or a visitor's answer.
- **Editing an item never changes its status.** Status changes are explicit actions (publish / move-to-draft); a content edit must not clobber a booking.
- **Archived wishlists are owner-only** — 404 for everyone else, including direct links (any owner still sees them). That covers its items too: listing them, proposing, booking or unbooking, and editing or withdrawing a proposal. **A list and its items share one set of view rules**: `GET /api/wishlists/[id]` and `GET /api/wishlists/[id]/items` both admit a viewer through `getWishlistViewAccess` (`lib/utils/wishlistAccess.ts`: archived, visibility tier, membership, any owner's friends), so a new read that admits viewers to a list uses it too rather than re-deriving the rules. The item writes (`POST /api/wishlists/[id]/items`, `PATCH`/`DELETE /api/items/[id]`) refuse a non-owner on an archived list with `isHiddenByArchive`, answered like a missing list or item. So does every owner-only route on the list itself (its settings and delete, members, invites, kick, owners): `getOwnerAccess` hands no list back to a non-owner of an archived one, so they get exactly the `Wishlist not found` 404 of a list that doesn't exist, never the 403 that would confirm it does. That includes an owner who lost ownership mid-request, because the read that picks a refused owner write's answer goes through `getOwnerAccess` too. A non-owner of a list that isn't archived still gets 403. These routes check the session before they look the list up, so a signed-out caller gets the same 401 whether or not it exists, and the invite route rate-limits only once the caller is known to own the list. A new owner-only route on a list authorizes its caller through `getOwnerAccess` (not the bare `isOwnerOfWishlist`, which can't tell a hidden list from a refused caller) and keeps the same order; `test/api/archivedOwnerRoutes.test.ts` holds a table of these routes to add it to. One answer does confirm that an archived list exists, and is accepted (WIS-202): slugs are unique across every list, so `PATCH /api/wishlists/[id]` answers 409 `That URL is already taken.` for a slug any other list holds, archived ones included. (A list that isn't archived is confirmed by any read of its slug anyway: a private or friends-only one answers 401/403, not 404.) An owner-chosen slug is a public URL by nature, and the 409 says only that some list holds it, not whose list or what's on it (a generated slug's random suffix makes it hard to guess anyway). Trying slugs that way is rate-limited instead (`wishlistSlug`, see the rate-limiting item). The other is a gifter's own reservation on it (WIS-124): their Booked page says "This list was archived" (`listArchived`), if they could open the list but for that, and shows the reservation frozen, as its snapshot alone, with nothing live of the list or the item (see the gifting and search items). Leaving (`DELETE /api/wishlists/[id]/members/me`) is the one exception for members: they may still leave an archived list, as any other (their bookings are freed and their pending invites cancelled), since that only takes their access away. But the leave route also checks the session first, and answers anyone else who isn't on an archived list with that same `Wishlist not found` 404, never `You are not a member`. That includes someone taken off it mid-request, so the answer comes from a fresh read through `getOwnerAccess` (`test/api/archivedLeave.test.ts`). A co-owner whose leave finds they've already lost ownership is anyone else by then: if a demotion left them a member, they leave as one.
- **An archived list's pending `member` invites are paused** (`isInvitePaused`, `lib/utils/wishlistInvites.ts`), since joining would leave the invitee on a list they can't open. They stay pending, but the invitee's invites read (`GET /api/users/me/invites`) leaves them out, and so does their notifications feed (`pausedInviteWishlistIds`: the feed, its unread count and mark-all-read skip the unanswered `wishlist_invite` row, which isn't deleted). Accepting or declining one answers the `Invite not found` 404 without claiming it, so to a non-owner an archived list stays indistinguishable from a missing one (it can be declined once unarchived), and an owner issuing a new one gets 409 `Unarchive this list to invite members` (checked last, so an invite refused for another reason gets that answer). Accept re-reads the list once the invitee's membership row is written, and if it was archived in the meantime, deletes the row it created (never one they already held) and reopens the claim, with the same 404, so a member invite never ends in a membership on an archived list. If that row is already gone by then, a kick took it, and the invite is withdrawn instead, as the kick's own cleanup would have. Unarchiving resumes them all. `owner` invites, promotions included, work as on any list.
- **A list you can't open looks the same in the browser, whatever the reason, and is answered where you asked.** The wishlist page never redirects or toasts when a read of the list or its items is refused (the route's own 401/403/404: `isRefusal`, `readResource` and `ReadRefusedError` in `lib/utils/resourceRead.ts`). It shows `WishlistUnavailable` at the list's URL, one state for a missing, private, friends-only or archived list, chosen only by whether the viewer is signed in (signed out, it offers Sign in back to this URL), never by the status or its wording, which differ (`getWishlistViewAccess` answers a signed-out viewer 401). A refused poll switches to it and stops polling, once a read of the list by its id agrees: a co-owner may have given the list a new slug, and then the page follows it to its new URL instead. Anything else (a 5xx, the network) may pass: a first load shows `LoadError` with Try again, and a poll that fails that way keeps the list. An unknown username gets the same treatment on the profile page ("No one goes by @name"), and a URL no route matches gets `app/not-found.tsx`.
- **Share tells a list's owners who its link opens for, and decides nothing.** `ShareButton` given `owner` (the list page passes it to owners only) opens a `Menu` whose header is `LINK_AUDIENCE_TEXT[linkAudience(list)]` (`lib/utils/shareLink.ts`): anyone, friends of any owner and people on the list, people on the list, or, archived, the owners only. That is `getWishlistViewAccess` read for the owner, and `test/api/shareLinkAudience.test.ts` pins the two together, so change them together. Everyone else (members, visitors, profiles) gets the plain share: the phone's share sheet (`navigator.share`) on a touch device, else a copy of the link, and a cancelled sheet says nothing. Whether there's a share sheet is read in the browser only (`canUseShareSheet`: on the click, or through `useSyncExternalStore` with `false` on the server), never in a render the server also does. An archived list shows no Share at all, as before. The link shared is the list's canonical one (`/wishlists/<slug or id>`), never `location.href`.
- **Search returns only lists the searcher could open.** `/api/search` matches lists with `viewableWishlistsFilter` (`lib/utils/wishlistAccess.ts`), the query form of `getWishlistViewAccess`, for a listing that can't check each document one by one. A table test over every visibility / archived / relationship combination (`test/api/viewableWishlistsFilter.test.ts`) pins the two together, so change them together. A list the searcher doesn't own or belong to also stays out of their results if any of its owners shows their wishlists to friends only and the searcher isn't that owner's friend. The Booked page's read of a gifter's reservations (`readReservationWishlists`, `lib/utils/reservationWishlists.ts`) uses the same filter, inside its one query for the lists, to return a list's live slug and occasion only while the gifter can still open the list: a Reservation outlives leave, kick, archiving and a list going private, and none of those may leave the gifter seeing the list's date, or its current slug (made from its name, and an owner can change it). Otherwise they're `null`, and the reservation's `listOpen` is false: its card names the list (from its snapshot) without a link, as no longer available to the gifter (a legacy list with no slug yet is still open, and linked by its id). That one query matches with `viewableUnlessArchivedFilter` (the same rules with archiving left out) and applies `isHiddenByArchive` itself, so a list that only its archiving hides from the gifter is only marked as such (`listArchived`), which freezes its reservation: no live item status or `stillReserved` either (see the gifting item). One they couldn't open anyway (kicked, say) is never marked archived, so they can't follow its archiving and unarchiving, or tell it from a deleted list. Only the snapshot the record took, the list's id and, for a reservation, its item's id (which Release unbooks), whether the gifter can still open the list (`listOpen`, which says nothing but their own access, so it's theirs to know), whether it's archived, and, unless it is, the live item's status (whether that should stay on a list out of their reach for any other reason is WIS-295) come back regardless. The gift history reads nothing of the live list at all: an entry (`serializeGiftLog`, `lib/utils/giftHistory.ts`, the one shape both `GET /api/users/me/gifts` and the gift route's answer give) is only the snapshot the `GiftLog` took and its list's id, and doesn't link the list.
- **`profileVisibility: 'friends'`** hides the bio and the browsable wishlist list from non-friends, but keeps username/avatar public. Per-wishlist visibility is a separate axis and is never bulk-mutated as a side effect.

## Conventions

- **Money** is stored as integer **cents**. Currency-code casing is **not uniform** in the DB: `Item.price.currency` is lowercase (to match the rates format), while `Wishlist.currency` and `User.defaultCurrency` are uppercase — normalize before comparing. Conversion routes through USD (`rate` = units per USD). Use the shared helpers in `lib/utils/currency.ts` / `currencyRates.ts`. **Other people's prices show in the viewer's currency (D9)**, as Settings and the currency prompt promise: on someone else's list the Prices control starts on the viewer's `defaultCurrency`, on an owner's own list on each item's currency, and a pick is remembered for that account, separately for their own lists and other people's, in that browser only (`lib/utils/listPrices.ts`, `useListPrices`; picking the context's default forgets it, and picking "· your default" is kept as that rather than as its code, so either way a new default in Settings is followed). Prices is only offered when some priced item isn't in the viewer's currency, and only once the exchange rates have loaded (they're only read then): without it every price shows in its own currency, so the control never names a currency the cards aren't in. Compare codes uppercase. **Every price shown goes through one formatter**, `formatPrice` (`lib/utils/currency.ts`, `Intl.NumberFormat` with the currency's symbol, grouping and decimals, Latin digits), in the locale `useViewerLocale` (`lib/hooks/useViewerLocale.ts`) gives: the browser's, but the fixed `PRICE_FALLBACK_LOCALE` in a server render and in the render that hydrates it, so the two never disagree. Code that only runs on the server (a share card, an email) passes no locale and gets that fixed one. A converted price is only as good as the day's rate, so it's shown with `formatApproxPrice` ("≈ €247") and the original on a muted line under it (`convertedPrice` says when that applies); a price in its own currency is shown exactly. The item form's price field is text (`inputMode="decimal"`), not a number field: `parsePriceInput` reads it with either decimal separator and grouping ("1 234,50", "1,234.50"), and a lone separator before three digits ("1.234") as the viewer's locale writes numbers, so a typo is refused rather than read as 1000 times the price; `formatPriceInput` fills and refills it (on blur) in the cards' format; and an amount it can't read is refused, never saved as no price.
- **A user's currency is suggested, never guessed for them.** Every account starts on `defaultCurrency: 'USD'`, and the dashboard's one-time prompt (`components/CurrencyPrompt.tsx`) offers anyone still on it who hasn't answered it yet (`currencyToOffer`) the currency of where their browser is. `suggestCurrency` (`lib/utils/currencySuggestion.ts`) works it out in the browser only, from the time zone, then the language's region, and only ever suggests a currency in `CURRENCY_OPTIONS`: no IP geolocation, no server-side `Accept-Language` guess. A zone that names a place decides on its own (one in a country whose currency we don't offer suggests nothing, rather than what the language says), and a USD suggestion shows no prompt. Either answer sends `currencyChosen: true` to `PATCH /api/users/me`, which stamps `User.currencyChosenAt` with the server's clock, as it does for any request that sets `defaultCurrency`: a Settings save that changes the currency (which is when `profileChanges` sends it) is an answer too, USD included. So the stamp isn't a setting and stays out of `ProfileSettings`, and the form never sends it. It's written with `$min` in the route's one write, so the earliest answer stands and none can clear it, which is why the field has no default: absent until answered, never null, which `$min` would keep. The session carries it only as the boolean `currencyChosen`. Lists keep the currency they have: `Wishlist.currency` keeps its schema default, so a list that never stored one stays on USD.
- **An occasion's date is a calendar date, not a timestamp.** `Wishlist.occasion.date` is a `YYYY-MM-DD` string with no time zone, and "today" is the viewer's local date, so a countdown is only worked out in the browser: read the date with `useLocalToday` (`lib/hooks/useLocalToday.ts`), which is `null` in a server render and in the render that hydrates it, so a server whose date differs can't cause a hydration mismatch. Do the date arithmetic with `lib/utils/occasion.ts` (`nextOccurrence`, `daysUntil`, `formatOccasionLabel`, `occasionSortKey`), never by parsing it into a `Date` or with `toISOString()` (that's the UTC date). **A yearly occasion stores no real year**: only its day and month matter, so `occasionSchema` replaces whatever year it's sent with (a birth year, say) with the placeholder leap year `YEARLY_PLACEHOLDER_YEAR` (2000, so Feb 29 stays valid; `normalizeOccasionDate`), and the model refuses a yearly one on any other year. Never show that placeholder: a yearly occasion is shown by its next occurrence, and the settings form asks it for a day and month only. A one-off keeps its real year, and isn't refused once it's past. An occasion goes to whoever can see its list, and never decides who that is.
- **Every button and field is sized from one scale**, and hand-rolled ones are out: a control matches the fields beside it, and a row of controls shares one height. **`sm`** 36px (`h-9 text-sm`, 16px icons): toolbars and filters, page-header actions, actions in list rows and compact cards. **`md`** 40px (`h-10 text-sm`, 16px icons): card action rows, dialogs without fields (`ConfirmDialog`, the crop dialog), the header's round buttons. **`lg`** 44px (`h-11 text-body`, 18px icons), the default: every form field and form button, a page's primary call to action. **`xl`** 48px: the landing page only. A labelled button is a `Button` (`variant`, `size`, `shape="pill"` for page chrome and every page-header action, `icon` for a leading icon drawn at its size). It's `type="button"` unless it says otherwise, as `IconButton` is, so a form's submit button says `type="submit"`. A link that looks like one takes `buttonClassName` (`components/buttonStyles.ts`), which `Button` uses too. An icon-only button is an `IconButton`, whose type requires a `label` (its accessible name): 32px (`xs`, the default) for a close or clear button inline with text, otherwise square at its row's height, always with an 18px icon (`iconButtonClassName` for a link). Only `Button` carries the primary glow and hover, and every button has the one disabled look. `Select` keeps its own size names: its `sm` is 36px and its `md` 44px (the scale's `lg`), the one to put beside a form field. A toolbar that has to fit a phone gives a `Select` a shorter `valueLabel` for its trigger (a list's Sort and Prices), and the menu keeps the full labels. A text field is an `Input`, `Textarea` or `SearchField` (`lg`, or `sm` in a toolbar), with `leading` / `trailing` content inside its border (a prefix, a status, the clear button) rather than a hand-built wrapper, and focus from `field-focus` (see the base-CSS item below). Wrap it in a `Field` (label, `helper`, `error`): the control takes the field's id, is described by the helper and the error, and is marked `aria-invalid` while there's an error. A `Field` reaches every `Input` or `Textarea` inside it, so a popup's own search box inside one (the item form's currency picker) stays a plain `<input>` with `inputClassName('sm')`, and a `SearchField` outside one needs an `aria-label`. A label or helper beside a control that isn't one of those (a `Select`, `ImageUpload`) takes `FIELD_LABEL` / `FIELD_HELPER` (`components/fieldStyles.ts`), and a field-like trigger `inputClassName()`.
- **Text is sized from one type scale.** `@theme` in `app/globals.css` adds `text-body` (15px: prose, an empty state's body, a compact card's title, an `lg` control's label), `text-meta` (13px: the meta line under a title), `text-badge` (11px, semibold: badges, pills, small uppercase labels) and `text-title` (17px: a grid card's title, the wordmark), in rem with their own line heights. Everything else is a Tailwind step: a page's h1 `text-3xl font-semibold tracking-tight` (`sm:text-4xl` on a list, the dashboard greeting and a profile), a section's h2 `text-xl`, a dialog's title `text-xl`, a panel's and a `ConfirmDialog`'s `text-lg`, a sub-section's `text-base`, UI text `text-sm`, helper text `text-xs`. Headings are semibold, and bold is only for stat numbers. Never an arbitrary `text-[Npx]`: `test/unit/typeScale.test.ts` fails on one in `app`, `components` or `lib`; a size the scale lacks is a new token. **Copy is sentence case** ("Save changes", "Delete item", "Discard changes?"), a proper name aside, and a pending label ends in "…", never "...".
- **One word for each act (D1), in every string a user reads** (buttons, `aria-label`s, toasts, dialogs, notifications, emails, metadata, the landing page). A member **reserves** an item and **releases** it, and sees "Reserved by you", or "Reserved" when someone else has; never Book, Unbook, Booked or claim. A gifter **marks it as given**, and it goes to their **Gift history**; never "gifted". An owner **marks it as received**, and it shows as **Received** (undone with "Mark as not received"); never Completed. The visibility tiers are **Public · Friends · Invite only** (`visibilityMeta` in `lib/utils/visibility.ts` holds each one's label and helper; a private list is never "Only me" or "Private", since its members and co-owners can open it). This is copy only: the stored names (`booked`, `completed`, `private`), the `/booked` route and API fields keep theirs. An owner never sees "Reserved" as a status, and no copy names a proposer or who reserved something.
- Prefer the shared `Select`, `Menu`, `ConfirmDialog`, `BaseModal`, `Skeleton` components over bespoke ones, and `Cover` for any list or item image (it shows the gradient placeholder when the image is missing or fails to load). On a list's own page the banner is a short full-width strip above the title (`WishlistCover`: 2.4:1 on a phone, 3:1 capped at 240px from `sm`), and a list with no banner has no strip at all. Banners stay cropped to 16:9, the shape list cards and share cards show them at, and the strip trims their top and bottom with `object-cover`. The rest of the kit, which replaced every hand-rolled copy (don't build another):
  - **`EmptyState`** (icon, title, body, `actions`; tone `default`, `muted` or `error`): every empty page, list, grid and search, in a dashed frame where the content would be, and, `framed={false}`, a page that can't show what was asked for (not found, unavailable). `LoadError` is its `error` tone with Try again, for a read that failed.
  - **`Badge`** (`sm` / `md`; tone `neutral`, `info`, `success`, `warning`, `danger` or `glass` over a cover image): a label, a count, a cover pill. An item status is `<Badge status={statusMeta(…)} />` and nothing else, so its label, icon and fill come from the one map. `badgeClassName` gives a label that lays itself out (`OccasionLabel`) the same look.
  - **`Panel`** (`rounded-2xl border bg-surface shadow-sm p-5 sm:p-6`, a `text-lg` title and muted description; `as="form"`; `variant="list"` for a bordered header over `PanelRow`s divided by a line) and **`PanelSection`** for a sub-section under a line: Settings, Welcome, a list's People and Settings tabs, the currency prompt.
  - **`SegmentedControl`** (`sm` 32px, `md` 36px segments): one choice out of a few side by side (a list's visibility, privacy settings, an item's status, the followers dialog's two lists). It's a WAI-ARIA radio group, one Tab stop on the selected segment, whose arrow keys (wrapping), Home and End move and select; a test finds a segment with `getByRole('radio', { name })`. (The account menu's theme is a `MenuRadioGroup` instead.)
  - **`Callout`** (`info`, `warning`, `danger`, on the status tokens): a notice in a form or page. `danger` is an `alert`, the others a `note`.
  - **`Spinner`**: the one spinner, for a wait inside something already on screen (an upload). A page that's loading shows a skeleton of its own layout instead, built from `Skeleton` blocks (never a raw `.skeleton` element).

  When a page's layout changes, **update its skeleton to match**. **Every dialog but `ConfirmDialog` is a `BaseModal`** (`CreateWishlistModal`, `FollowListModal` and `ImageCropModal` included): a panel portalled to `<body>`, `size` `sm` 24rem, `md` 28rem or `lg` 32rem (the default), with a standard pinned header (a `text-xl` title and a 32px close `IconButton`, named by `closeLabel`), a scrolling body, and an optional pinned `footer`, right-aligned, Cancel first and then the primary action. `headerContent` pins controls under the title (the followers dialog's tabs), and `onSubmit` makes the panel the `<form>`, so a `type="submit"` button in the footer submits the body's fields (Enter in a field too). Don't build a dialog's shell by hand. Every dialog manages keyboard focus through `useFocusTrap` (`lib/hooks/useFocusTrap.ts`): focus moves in on open (Cancel, the create form's name field through its `autoFocus`, or else the close button unless the content has an `autoFocus`), Tab stays inside the topmost of them that's open, even one stacked over another from inside its content (the crop dialog, rendered in an item or create form and portalled over it), and focus goes back to the opener on close. While a dialog's form is busy (the hook's `busy` option: `BaseModal`'s `isSubmitting`, which also blocks every way out, or its `busy`, which doesn't: a running crop can be cancelled at once), focus is held on its panel instead of dropping to `<body>` with the disabled control, and goes back to that control, if it can take focus again, when that ends with the dialog still open. A trap only counts the Tab stops inside its dialog, so a popup a control portals out of it (the `Select` menu, on `<body>`) keeps focus on that control instead of having stops of its own. `Select` is a WAI-ARIA select-only combobox (a test finds its trigger with `getByRole('combobox', { name })`, not as a button): the trigger is its one Tab stop, on a page or in a dialog, and keeps focus while the menu is open. Enter, Space or an arrow key opens the menu on the selected option, the arrow keys, Home, End and type-ahead move the active option through `aria-activedescendant`, Enter or Space picks it, and Escape or Tab closes the menu. The open menu's keys stop at the trigger, so its Escape doesn't also close the dialog around it. The invite form's username field (`InviteMemberForm`) is an editable combobox on the same model (`getByRole('combobox', { name: 'Search by username' })`): focus stays in the field, ↓ and ↑ move the active suggestion, Enter picks it (with none active, Enter sends the invite as typed), and Escape or Tab closes the list, its Escape stopping at the field too. Its suggestions say who is on the list already (Owner, Member or Invited, worked out in the browser by `listStatusByUsername`, `lib/utils/inviteSuggestions.ts`, from the owners, members and pending invites the page has loaded) as disabled options, and a member's offers **Make co-owner instead**, which opens the page's own Make owner confirmation and promotion invite, so there's one path to it. A new overlay uses the same hook, and a new portalled popup keeps focus on its control the same way.

- **A read that failed is never shown as empty.** A page's empty state ("No wishlists yet", "You're all caught up", "Nothing reserved yet") is a claim about the user's data, so it only follows a read that succeeded. Track a failed load apart from an empty one: when a page's first load fails (a 5xx, the network), it shows `LoadError` in the content's place ("Couldn't load your …", with Try again, which re-runs the read), with no empty-state copy or call to action and no toast, and nothing that counts what it couldn't read (the dashboard's tiles, the wishlist page's status chips and toolbar). A count read on its own (Reserved by you, followers) shows a placeholder until it's known and a dash if it couldn't be, never a 0. Settings shows no form until its first read lands, since one filled with defaults would look as if the account had lost them. Once something has been shown, a later read that fails (a poll, a refresh, a toggle) keeps it, as before. This covers the dashboard, Notifications, a profile and its followers dialog, Settings, Reserved, Invitations, All items and the wishlist page's items.
- **Confirmations never say a reservation goes when it stays.** Leaving, removing someone and moving an item to draft free items but keep the reservations, and deleting a list keeps them too (see the invariants), so no copy says a booking is removed, cancelled or deleted by them. The copy for leaving, removing and deleting lives in `lib/utils/confirmationCopy.ts`, with the gifter's own toasts after accepting an owner invite and after leaving, which add the count the API answers with through `releasedGiftsNote`: after an accept, `cancelledReservations` (the reservations that go from their Reserved page, which can be more than the items it freed), and after a leave, `unbookedItemsCount`. Only the gifter's own copy says what of theirs is kept, and only it carries a count: the leaving member's comes from the items already on their page. Copy an owner reads may say what happens to a reservation in general ("if someone reserved it"), never whether anyone did or how many. A danger `ConfirmDialog` that deletes nothing passes its own `icon` (`logout` for leaving, `user-minus` for removing someone) instead of the trash can, and these dialogs' titles are sentence case.
- **A menu of actions is the shared `Menu`** (`components/Menu.tsx`, a WAI-ARIA menu button: a test finds its trigger with `getByRole('button', { name })` and its items as `menuitem`s). The header's account menu (`AuthButton`) is one too: a custom `trigger` (the avatar and name, told whether it's open), a `header` that isn't an item (avatar, username, and the email, which only its owner ever sees, outside the `role="menu"` element so the keys skip it), link items (`href`, with `external` for another site's page, opened in a new tab), and the theme as a `MenuRadioGroup` (`menuitemradio`s in the arrow-key order, which stay open when picked). It renders in place, not portalled, so focus moves into it: Enter, Space (on its keyup, or Firefox would click the item focus lands on) or ArrowDown opens it on the first item, ArrowUp on the last, and a pointer opens it with the menu itself focused. The arrow keys (wrapping), Home, End and a typed letter move between items, and Escape, Tab, a click outside or focus leaving closes it, Escape and Tab with focus back on the trigger. Picking an item puts focus back on the trigger before its action runs, so a dialog the action opens returns focus there when it closes, and focus never strands on `<body>`: an item that goes away under it (a poll) leaves it on the menu, and a menu that closes with it lost puts it on the trigger. A held item (`disabled`) is `aria-disabled`: still in the arrow keys, but picking it does nothing. - **Uploads are sanitized and owned.** Every image is re-encoded with `sharp` on upload (`app/api/upload`), which strips EXIF/metadata and bakes in orientation. **An upload has to be the type it declares**, because sharp picks its decoder from the bytes, never from `file.type`: the route answers a mismatch with the same 400 as an unsupported type, first when the leading bytes lack the declared type's signature (checked before sharp reads anything, so only the declared type's loader ever gets the file), then when the format `metadata()` reports isn't the declared type's (an AVIF must be `heif` with AV1 compression, since HEIC shares libheif's loader), before any pixels are decoded. **librsvg never parses an upload**: also before sharp reads anything, whatever the declared type, the route refuses with that same 400 any file libvips' own SVG sniff would claim (`sniffsAsSvg`, which mirrors libvips' `svgload` `is_a`: an `<svg`, in any case, before the first byte that isn't valid UTF-8, or gzip's magic), since a GIF's or WebP's signature can start such a file. When an image field (`Item.imageUrl`, `User.image`, `Wishlist.bannerUrl`) is replaced or its record deleted, free the old blob with the helpers in `lib/utils/blob.ts` — but **only ever delete our own blobs** (`isOwnBlob`, which matches our exact store host, derived from `BLOB_READ_WRITE_TOKEN`); a user-pasted external image URL must never be deleted. Free the image the write actually replaced, never the one the request read before it: two owners replacing one image at once both read the same one, so freeing that read frees it twice and orphans the image the first put in its place. So an edit that replaces or clears an image takes the old value from its own write (`findOneAndUpdate` with `returnDocument: 'before'`) and hands it to `freeReplacedImage`, and deleting an item frees the image of the document `findOneAndDelete` returned. An edit that sends the image the field already holds (`isSameImage`: the item review form always sends it) doesn't write it at all: written back over a replacement that landed after the read, it would restore an image that replacement has already freed. Because whatever a record holds gets freed, **you may only attach blobs from your own `uploads/<yourId>/` folder**: every route that writes one of those fields checks `canAttachImage(next, actorId, current)` and returns 400 `FOREIGN_IMAGE_ERROR` otherwise. Keeping the value already on the record is allowed (a co-owner's upload on an item or banner, a proposer's image on an approved proposal), and external URLs are always allowed. Two items never share a blob, since freeing one would break the other: saving a copy of an item ("Save to my list", `sourceItemId` on `POST /api/wishlists/[id]/items`) copies the source's blob into the caller's own folder with `copyBlobToUploads`, against their quota, and saves without the image (with a `notice` in the reply) when it doesn't fit. The one other kind of blob is a **snapshot** under `snapshots/`: once a booking's reservation is written, `snapshotReservationImage` copies the item's image there and points the reservation at the copy (best-effort: on failure it keeps the item's URL), so the gifter's `Reservation` / `GiftLog` image survives the owner deleting the item or replacing its image. Snapshots count against nobody's quota (a booking-blind owner's must never move because someone booked) and fail `canAttachImage`. Free them only through `lib/utils/reservationSnapshots.ts`: `deleteReservations` for any reservation that ends without a gift, `releaseSnapshots` when a rebooking replaces one or a gift-log entry is deleted. Marking the gift takes the reservation in one atomic delete and hands its snapshot to the `GiftLog`, which keeps it; a snapshot has one holder at a time, so hand it on atomically or a concurrent dismiss frees what the log shows. Never free a reservation's or gift log's image with `deleteOwnBlob`: an older one (or one whose copy failed) holds the item's own blob.
- **Schema migrations are HTTP endpoints** under `app/api/migrations/<name>/route.ts`, built with `createMigration` (`lib/utils/migration.ts`) and gated on the `X-Migration-Secret` header. Run with `curl -X POST -H "X-Migration-Secret: $MIGRATION_SECRET" <host>/api/migrations/<name>`. There are none in the tree right now — the co-ownership set and `dedupe-pending-invites` were applied to every environment and deleted (see git history). When you add one:
  - Make it **idempotent**, so re-running is free and a partial run can be finished by running it again.
  - Decide its **deploy ordering** and say so in the docstring. An _additive_ migration (only writes new fields) is safe to run before the deploy, because the live old code still reads what it needs. One that removes or moves data the old code depends on must run **after**, or it breaks the running deployment.
  - If the reading code needs a fallback for the un-migrated shape, gate that fallback on the new field being absent, and delete it in a follow-up once the migration has run everywhere. Don't leave fallbacks behind — they quietly become unreachable code that still has to be reasoned about.
  - A new **unique index** on a collection that may already hold duplicates needs one that dedupes and then builds the index itself (`Model.createIndexes()`). Mongoose's `autoIndex` is on (`lib/mongodb.ts` doesn't change it) but fails such a build silently — the error only reaches the model's `'index'` event — so without the migration the index just never appears.

- **Rate limiting goes through `enforce()` / `checkRateLimit()` in `lib/rateLimit.ts`** — never hand-roll an in-memory counter (Vercel's per-request instances don't share it). Add a new surface by adding a `SPECS` entry (tokens/window/policy/keyKind) and calling `enforce('<name>', key)` right after the auth/access check, returning its response if non-null. A limit that guards one kind of change is spent only by a request that makes it: `wishlistSlug` (10 per 10 min per user) runs inside `PATCH /api/wishlists/[id]`'s slug branch, once the caller is known to own the list and only when the slug sent differs from the list's, so a settings edit that leaves the URL alone never spends it (`test/api/wishlistSlugLimit.test.ts`). Build keys only with the helpers: key **authed** writes on `userKey(session.user.id)`; key **public** reads on `ipKey(request.headers)`; key the sign-in email path on **both** `emailKey(email)` and `ipKey`. A key's brand must match its entry's `keyKind` (a type error otherwise, so pass the limiter name as a literal), because every block logs one JSON line `{"event":"rate_limited","name","keyKind"}` for tuning `SPECS`, and that line must never carry the key itself (it's an email, IP or user id); the same goes for any other log line in the limiter. Choose `fail-open` for user-facing reads/writes and `fail-closed` for cost-bearing email sends. The policy covers the store **timing out** as well as throwing: on a slow Redis `@upstash/ratelimit` doesn't throw but resolves `{ success: true, reason: 'timeout' }` after `STORE_TIMEOUT_MS`, which `run()` treats as a store error — so never act on the SDK's `success` without going through `run()`. Limiting is **disabled** when neither `UPSTASH_REDIS_REST_URL`/`_TOKEN` nor their `KV_REST_API_URL`/`_TOKEN` fallbacks are set (CI/tests) — tests inject a fake via `__setRateLimiters`, they don't need Redis. A `.env` pulled from Vercel carries the `KV_*` pair, so local dev _does_ rate-limit against that store.
- **A magic link is only sent by the sign-in form's server action** (`requestMagicLink`, `app/auth/signin/actions.ts`). It checks the Cloudflare Turnstile token with `verifyTurnstileToken` (`lib/turnstile.ts`) before anything else, then calls Auth.js's server-side `signIn` inside `asVerifiedSignIn` (`lib/signInEmail.ts`). Auth.js's own `POST /api/auth/signin/<provider>` answers 403 (`isMagicLinkSignInPath`), and a request that didn't start inside `asVerifiedSignIn` is refused by the `signIn` callback (`email.verificationRequest`) and by `sendVerificationRequest`, so any new way to send a sign-in link goes through that action, never around it. Turnstile is on only when both `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` are set (`getTurnstileKeys`), and `lib/env.ts` refuses one without the other. The sign-in page reads them per request and hands the site key to the form, so the widget and the check never disagree. Only the token can fail the check closed, a missing one included. That one is still put to Cloudflare (as an empty response), because the form sends none when Turnstile's script couldn't load or run, which is what a Cloudflare outage looks like in the browser. When Cloudflare gives no verdict (unreachable, no answer within `TURNSTILE_VERIFY_TIMEOUT_MS`, a 5xx, `internal-error`, a secret it rejects), the check fails open and logs `turnstile_unavailable`, and the fail-closed sign-in limiters stay the backstop. Its log lines carry no token, IP or email.
- **Email HTML escapes every user-controlled value.** `getEmailTemplate` (`lib/email.ts`) escapes its plain-text fields (title, greeting, button text, URLs). `contentHtml` / `footerHtml` are raw HTML, so pass every value you interpolate into them (a wishlist name, a display name, an address) through `escapeHtml`: a wishlist name is free text, and unescaped it can put a live link in a mail sent from our domain. Button and fallback URLs must be links we build, never a user-supplied URL, because escaping doesn't vet the scheme. **A subject carries no free text**, the wishlist name included: escaping can't stop Gmail, Outlook or Apple Mail auto-linking URL- or domain-looking text, and the subject is what the inbox shows before the mail is opened, so a list named `Claim your gift at https://evil.example/login` would read as our own call to action (WIS-102). The invite email's subject names the inviter by username and the role (`@ann invited you to a wishlist` / `@ann invited you to co-own a wishlist`, `invitationSubject`), and "Someone" for an inviter with no username rather than their free-text `name`. The name stays in the body, but only inside the sentence that names the inviter (escaped in the HTML), never a line of its own, the heading included, since an inbox shows the body's first text as its preview; a client may still auto-link it there, which the operator accepted over refusing URL-like names. Plain-text parts take the raw value, so free text that goes into them must be one line, with no bidi embedding, override or isolate (U+202A–U+202E, U+2066–U+2069, which reorder the text after them, e.g. a domain read backwards), and must show something: the wishlist name's schema (`lib/validations.ts`) refuses line breaks and other control characters, those bidi controls, and a name that's blank once its invisible characters are removed (ZWJ and ZWNJ stay allowed inside a visible name, since emoji sequences and Persian need them), and any new free-text field you put in an email needs the same checks.
- **Server logs carry no personal data**: anyone with project access reads them. Never log a user's email or user id, anything that says who is on, left or booked on which list, or a count of someone's bookings; a success path needs no log line. ## Keep docs current

When a change affects how the project is set up, run, or structured, update the docs in the **same** change — stale docs are worse than none:

- New/changed/removed **env var** → update `README.md` and `.env.example`.
- New/removed **npm script**, dependency, or tech-stack change → update `README.md`.
- New user-facing **feature** or removed one → update the README feature list.
- New **convention, invariant, or workflow** for contributors → update this `AGENTS.md`.
- **Deferred ideas and follow-ups** go to Linear (Backlog), not into a file in the repo — design notes for a large feature belong in its Linear project description.
