# Screens & client behaviour

AGENTS.md links here for how each screen reads, updates and lays out its data on the client.

## Data loading & mutations

- **A failed read is never shown as empty.** Empty states ("No wishlists yet", "Nothing here yet", "Nothing reserved yet") only follow a successful read; track failed apart from empty. Failed first load (5xx, network) → `LoadError` in the content's place ("Couldn't load your …", Try again re-reads), no empty copy, CTA or toast, nothing counting what wasn't read (wishlist page chips, toolbar). A standalone count shows a placeholder until known and a dash on failure, never 0; Needs you omits the row (never "nothing to do"). Settings shows no form until its first read lands. Once shown, a later failed read (poll, refresh, toggle) keeps content. Applies to dashboard, Activity (feed and pinned invitations separately), profile and followers dialog, Settings, Reserved, All items, wishlist page items.
- **Live reads go through one layer** (WIS-376, `lib/hooks/useLiveRead.ts`): `useLiveRead` holds a screen's read (`data`, `loaded`, `failed`, `loading`, `refresh`, `setData` for optimistic changes) and applies the rule above (a failed first read is `failed`, never empty data; a later failure keeps what's shown); it judges every read against the screen's `MutationTracker` (a read stale against a mutation is dropped and re-read once idle, unless nothing is shown yet: a first load lands) and drops a read older than one already shown (a stale answer asks for a re-read only if no read sent since the mutations settled is on its way). `resetOnNewRead` clears what's shown in the render a new `read` arrives in (every read keyed on the signed-in account uses it, so another account's data never shows for a frame); `merge` lands an answer into the data as shown instead of replacing it (Reserved's `mergeRefreshedList`, called once per answer outside rendering, `null` drops it). Under it: `usePolling` (every `POLL_INTERVAL_MS` while the tab is visible; the timer stops while hidden), `useRefreshOnReturn` (a read when the window is focused, or the tab shown again or the browser back online in a focused window: a tab uncovered in a window the viewer isn't in waits for their focus, so the Activity feed, whose read marks rows read, never reads for nobody; the `visibilitychange` + `focus` pair of one return counts once, `RETURN_PAIR_MS`; with `onlyAfterAway`, as a polled screen uses it, only after the tab was hidden or offline), and `sharedRead` (concurrent reads of one key share one request, stamped as it goes out). It keeps **no cache of answers** across mounts or keys, only requests in flight: an answer depends on the viewer and their role (a member's list read carries reservations, an owner's never does), so a cached one shown in another view could leak. A new `read` (another list, Preview as visitor) becomes the only one whose answers land, synchronously in render, so a late answer to the old one never shows; the old data stays until the new read answers, and a failed first answer shows `LoadError`, never the old data. **Who polls:** the wishlist page's items (5s, Items tab only). Reserved and Activity read on return only, no timer: Reserved's changes are mostly the viewer's own, and every Activity feed read marks what's unread as read, so a timer would clear the badge for rows nobody looked at. Every live read goes through `useLiveRead` (WIS-441: the items, Reserved, the Activity feed, pinned invitations, the unread badge, Needs you's changed reservations; all but the items with no `pollMs`), never its own `focus` listener, read numbering or failure handling; a new screen that needs to stay live does too.
- **Mutations are optimistic and survive the 5s poll** (see `handleUpdateItem`; the wishlist page's items, poll and optimistic updates live in `useWishlistItems`, `lib/hooks/useWishlistItems.ts`, on top of `useLiveRead`): update locally, merge the server's single item, never let a stale in-flight poll overwrite fresher state. Item updates: `handleUpdateItem` → `updateItemOptimistically` (`lib/utils/itemListMerge.ts`); on failure undo at once (fields revert unless changed since), then reconcile with a read that may be dropped or fail (failure keeps the list). Every item mutation goes through `mutations.track` (`createMutationTracker`, `lib/utils/mutationTracker.ts`, also used by `usePendingInvites`), which drops polls landing during or read across one; so each is bounded by `withRequestTimeout` (`lib/utils/requestTimeout.ts`): unanswered within `ITEM_REQUEST_TIMEOUT_MS` → aborted, handled as failure. Abandoned requests may have landed, so retries must be safe (WIS-158): add/propose send an `Idempotency-Key` per submission (`createSubmissionKeys`, `lib/utils/submissionKey.ts`: same key while fields unchanged, new after a save or dialog close); `POST /api/wishlists/[id]/items` answers a seen key on that list with its item via `serializeItem`. Stored hashed with the sender's id (`scopedIdempotencyKey`, `lib/utils/itemIdempotency.ts`, `select: false`, never returned) under a unique partial index `{ wishlist, idempotencyKey }`: other accounts never match, racing attempts make one item; a member is never answered with an item they can't see (draft: 409). Owner delete answered 404 is done (`useDeleteItem` `notFoundIsDone`, no error); a proposer's stays an error (archived list gives the same 404 while the proposal exists). Reads are judged by send time (shared concurrent request; `useFetchItems` takes `mutations.stamp`, reports `sentAt`); a stale read is followed by a fresh one once idle (`mutations.rereadWhenIdle`); a stale non-silent read lands only while nothing is shown yet (first load).
- **Destructive actions offer Undo, not a confirmation** (WIS-387): the screen takes the thing away (or shows the change) at once, toasts it as done with **Undo** (`useUndoableAction`, `lib/hooks/useUndoableAction.ts`), and sends the request only once the Undo window (`UNDO_WINDOW_MS`, 5s) has passed, or sooner when the toast is dismissed or pushed off the stack; while the toast stack is hovered or focused the window holds and then runs on with the time it had left (`onPause`). Leaving the page (`pagehide`, or the tab hidden) sends whatever is waiting with `keepalive`, so pass `keepalive` through to the commit's `fetch`. Undo sends nothing, so nothing has to be reversed: no notification (kick, demote, remove, a group gift's cancel or hand-on), no released reservation, no freed upload; never add an Undo that writes the reverse for those. Hold the page's read guard over the window and the commit (`mutations.track(() => pending.settled)`, `useWishlistItems.deferItemChange`, the Reserved page's `deferCardAction` holding the card's busy id), so a poll can't bring the thing back while it waits; a failed commit puts it back with the request's own error. The queue (`lib/utils/deferredCommit.ts`) is app-wide and outlives the screen: navigating away sends it on time. A confirmation stays only where Undo can't be honest: deleting the account (typed confirmation), deleting or leaving a list (the page goes away), archiving (it ends the list's live group gifts, which unarchiving can't bring back), Mark as given and other changes that write for other people at once (convert a group gift, make owner, move to draft), and the given-gift Release warning. Reserve tapped during a pending Release is its Undo (Follow, Ask to join and re-ticking someone in a group likewise undo their pending opposite); any other change to the same item waits for its pending one to be sent and settle (`settlePending`), so the two can't race. The birthday nudge's dismiss is local only, so its Undo just clears it. The bulk delete (WIS-386) reuses the same helper.
- **Per-card actions use `useBusyIds`** (`lib/hooks/useBusyIds.ts`; Activity invitations and Follow back, Booked, People rows): wrap in `run(id, fn)`, disable on `busy(id)`. A card frees only when its own request settles and `run` ignores repeat calls in flight; don't rely on `disabled` alone. Booked re-reads its lists (tab return, after a 404) and merges with `mergeRefreshedList` (`lib/utils/listRefresh.ts`), not replace: a `ListChangeLog` records entries its actions added/removed so an older read can't undo them; `held: running` leaves in-flight cards as is.

## Wishlist page

- **Status chips filter and are never saved; sort is saved (D7).** On the wishlist page the chip, sort, search, budget, Prices pick and discreet mode's render-time hiding live in `useListFilters` (`lib/hooks/useListFilters.ts`). `FilterChips`: single-select with counts (radio group like `SegmentedControl`, sideways scroll on phone), from `lib/utils/listChips.ts`: owner All · Drafts · Proposals · Live · Received; member All · Available · Reserved by you · Your proposals; visitor none.
