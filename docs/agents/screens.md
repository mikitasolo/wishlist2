# Screens & client behaviour

AGENTS.md links here for how each screen reads, updates and lays out its data on the client.

## Data loading & mutations

- **A failed read is never shown as empty.** Empty states ("No wishlists yet", "You're all caught up", "Nothing reserved yet") only follow a successful read; track failed apart from empty. Failed first load (5xx, network) → `LoadError` in the content's place ("Couldn't load your …", Try again re-reads), no empty copy, CTA or toast, nothing counting what wasn't read (wishlist page chips, toolbar). A standalone count shows a placeholder until known and a dash on failure, never 0; Needs you omits the row (never "nothing to do"). Settings shows no form until its first read lands. Once shown, a later failed read (poll, refresh, toggle) keeps content. Applies to dashboard, Activity (feed and pinned invitations separately), profile and followers dialog, Settings, Reserved, All items, wishlist page items.
- **Mutations are optimistic and survive the 5s poll** (see `handleUpdateItem`): update locally, merge the server's single item, never let a stale in-flight poll overwrite fresher state. Item updates: `handleUpdateItem` → `updateItemOptimistically` (`lib/utils/itemListMerge.ts`); on failure undo at once (fields revert unless changed since), then reconcile with a read that may be dropped or fail (failure keeps the list). Every item mutation goes through `mutations.track` (`createMutationTracker`, `lib/utils/mutationTracker.ts`, also used by `usePendingInvites`), which drops polls landing during or read across one; so each is bounded by `withRequestTimeout` (`lib/utils/requestTimeout.ts`): unanswered within `ITEM_REQUEST_TIMEOUT_MS` → aborted, handled as failure. Abandoned requests may have landed, so retries must be safe (WIS-158): add/propose send an `Idempotency-Key` per submission (`createSubmissionKeys`, `lib/utils/submissionKey.ts`: same key while fields unchanged, new after a save or dialog close); `POST /api/wishlists/[id]/items` answers a seen key on that list with its item via `serializeItem`. Stored hashed with the sender's id (`scopedIdempotencyKey`, `lib/utils/itemIdempotency.ts`, `select: false`, never returned) under a unique partial index `{ wishlist, idempotencyKey }`: other accounts never match, racing attempts make one item; a member is never answered with an item they can't see (draft: 409). Owner delete answered 404 is done (`useDeleteItem` `notFoundIsDone`, no error); a proposer's stays an error (archived list gives the same 404 while the proposal exists). Reads are judged by send time (shared concurrent request; `useFetchItems` takes `mutations.stamp`, reports `sentAt`); a stale read is followed by a fresh one once idle (`mutations.rereadWhenIdle`); a stale non-silent read (first load) still lands first.
- **Per-card actions use `useBusyIds`** (`lib/hooks/useBusyIds.ts`; Activity invitations and Follow back, Booked, People rows): wrap in `run(id, fn)`, disable on `busy(id)`. A card frees only when its own request settles and `run` ignores repeat calls in flight; don't rely on `disabled` alone. Booked re-reads its lists (tab return, after a 404) and merges with `mergeRefreshedList` (`lib/utils/listRefresh.ts`), not replace: a `ListChangeLog` records entries its actions added/removed so an older read can't undo them; `held: running` leaves in-flight cards as is.

## Navigation & dashboard

- **Navigation lives in `AppHeader`, never a page.** Destinations (D3): Home, Reserved, Activity, Me (`navDestinations` / `activeDestination`, `lib/utils/appNav.ts`; Me = profile, or Settings without a username). `components/AppNav.tsx`: `TabBar` below `sm` (fixed bottom, icons+labels), `HeaderNav` from `sm` (Home · Reserved · Activity, Me = avatar); signed-in only, signed-out header unchanged. `aria-current="page"`: Home on `/`, `/wishlists/mine`, `/wishlists/shared`, `/items`; list pages mark none. Activity carries the unread count, the one unread signal (WIS-302, no bell): badge on tab icon and beside header link, max "9+", hidden at 0 and from AT, count in the link name ("Activity, 3 unread", `navAccessibleName`). Only `AppHeader` calls `useUnreadNotifications` (`lib/hooks/useUnreadNotifications.ts`) and passes it down (a second caller = a second reader per page and focus). It reads `GET /api/notifications` on sign-in, focus, `notifications-changed`, `invites-changed`; keyed on user id (new account re-reads, never sees the old count); drops reads landing after newer ones. Fire `notifications-changed` after anything changing unread. Account menu: profile, Settings, theme, Sign out only; new destinations go in the nav. Pages render `AppHeader` as first child of their outermost element; below `sm` it pads its bottom for the bar (`:has(> [data-tab-bar])`, `globals.css`), so pages don't; bottom-stuck elements sit `var(--tab-bar-space, 0px)` higher (Settings' Unsaved changes bar). Home shows ≤`HOME_SECTION_LIMIT` lists per section, then "See all (n)"; "All items" (`/items`) beside the Your wishlists heading. **Header holds its shape while the session loads** (WIS-209): placeholders take signed-in shape (links, avatar, tab bar) under `session-hint:`, Sign in's otherwise, from `data-session-hint` on `<html>`, set pre-paint by the root layout script from a localStorage flag (`lib/utils/sessionHint.ts`, synced by `SessionProvider`). Placeholders are exactly as wide as their replacement, hence the account button is the avatar alone (no variable-width name); new header actions need one; `e2e/app-nav.authed.spec.ts` checks no shift at 360 and 1280. A known session stays up through `update()` (which passes through `loading`), so no flicker on Settings save. Same on every page (WIS-301): wherever `status` is read use `useKnownSession` (`lib/hooks/useKnownSession.ts`), never `useSession`, so `loading` = no session known yet and pages keep content and `[status]`-keyed reads through `update()`.
- **Dashboard opens on Needs you and Coming up (D4, WIS-252).** Greeting row ("Good evening, Anna" + New list; no counts line; followers on profile), then those two blocks, each only when non-empty, then list sections; no stat tiles, no Featured hero. **Empty Home**: `StarterCard` (Create a list, Add a few things, Share it, with own `@handle` + Copy, `OwnHandle` / `useCopyProfileLink`) instead of lists; a generated handle (`isGeneratedUsername`) gets a one-time dismissible `UsernameNudge` (per account, localStorage) to Settings. Empty Shared with you: "Friends invite you by your username" + `OwnHandle`, centred, one line (WIS-312); Activity's empty state has no handle. Own handle only, never an email. **Welcome** (`/welcome`): username field starts empty (placeholder "e.g. maria_nowak"; generated handle only in the Keep button) under `AppHeader` `minimal` (wordmark + account menu). **Needs you** (`components/NeedsYou.tsx`): ≤3 rows (`NEEDS_YOU_LIMIT`), then See all in Activity; every kind gets one row before any gets two (`pickRows`: invitation, changed reservations, birthday nudge, currency prompt, then proposals). One read per row: invites, `GET /api/users/me/reservations/summary` (`useChangedReservations`: `withRequestTimeout`, re-read on focus, later failure keeps the count), and the lists already read. Pending/failed read → no row; empty block hidden. The list read keys on user id too, so another account signing in elsewhere never sees the previous one's proposals. **Counts:** `changed` (the summary's only field) is the caller's own reservations, identical to Booked's "Needs your confirmation" (both `readReservationLiveState`, `lib/utils/reservationLiveState.ts`, + `needsConfirmation`; `test/api/reservationSummary.test.ts`); owners hold none on own lists, so no reservation count reaches them. Banner, occasion, item count and name link only if the invitee could already open the list (`preview`, `getWishlistViewAccess` for them, WIS-273). Consent warning only when accepting releases something of theirs: their Reservations, counted (`yourReservations`, from their own Reservations, like accept's `cancelledReservations`), or uncounted an item still booked by them with no Reservation (a gift marked given, `holdsBookings`); both only on owner invites. Read/answer via `usePendingInvites` (`lib/hooks/usePendingInvites.ts`), never the feed: `GET /api/users/me/invites` is truth (notifications are best-effort). Hook: re-reads on focus and `invites-changed` (fired after answers), drops reads sent before an answer and re-reads when none in flight (`createMutationTracker`), `withRequestTimeout` on answers, keyed on user id, opens the list only for the last accept clicked (`createAcceptRedirect`, WIS-121). New invitation surfaces (Needs you, WIS-252) reuse hook and card. Feed re-reads on focus and `invites-changed`; answers given on the page are reapplied to older feed reads (`withInviteAnswers`). Pending invite row: no buttons/link (card answers it); answered row reads as the answer. Actor avatar only on `showsActor` types (`lib/utils/notifications.ts`: follow, invite, accepted invite, request to join), never proposal, demotion, removal, approved proposal. Actor from `Notification.actor` (kept by `createNotification(s)` only on those types), never `actorUsername` (usernames change hands); pre-`actor` rows show no face. `GET /api/notifications?actors=1` (Activity only; unread read omits it) adds `actorId`, `actorImage`, and for one-person follows `followingActor`, so **Follow back** (`POST /api/users/[id]/follow`) shows only if you don't follow them; multi-person follow opens `FollowListModal` in place. No avatar dot, no Invitations menu item. `/invites` stays a server redirect to Activity keeping its query (`activityPath`, `lib/utils/activityPath.ts`) for invite emails and sign-in callbacks.

## Wishlist page

- **Status chips filter and are never saved; sort is saved (D7).** `FilterChips`: single-select with counts (radio group like `SegmentedControl`, sideways scroll on phone), from `lib/utils/listChips.ts`: owner All · Drafts · Proposals · Live · Received; member All · Available · Reserved by you · Your proposals; visitor none. Count/filter by `displayStatus`: booked is Live to owners, no owner chip/count names a reservation, member counts never include drafts or others' proposals (`countListChips` drops them even if sent); Live + Received = "N items". Opens on All: actionable first, viewer's sort within groups (`orderListItems`: owner proposals, drafts, live, received; member available, reserved by you, own proposals, reserved by others, received); un-actionable (received, reserved by others) dimmed (`isDimmedInAll`, `WishlistItem` `dimmed`). Chip is per list and role only: `useListChip` (`lib/hooks/useListChip.ts`) keeps it in `?show=` via `history.replaceState`, not storage (back/refresh keep it); URL touched only while it names the list on screen (id or slug), restored when its own URL changes (new slug); a URL chip counts only if the role has it. Chips and toolbar (search, Sort, Prices: one row from `sm`; phone: search on its own row, Sort growing and Prices compact beneath, breakpoints only) hidden while loading, on failed read, or empty list. **Budget filter (WIS-326):** gifters only (signed-in, not an owner, some item priced), a separate toolbar field beside Prices: `BudgetFilter` "Under X" in the currency the Prices control shows (the account's default when Prices is on each item's own, or not offered); a new Prices pick keeps the typed text and re-reads it in that currency. Text kept in page state, never saved, cleared by Show all and on a list change. `lib/utils/budgetFilter.ts` converts each price with `convertPrice` (same as Prices) and compares integer cents, inclusive; items with no price, no rate or no rates yet stay visible. It narrows after `countListChips`, so chip counts never move. Not on `/items`. **All items (`/items`) = owner's view of the same page** (WIS-309): same `FilterChips`/owner chips, `countListChips` over items on lists the Lists filter includes, `orderListItems` / `isDimmedInAll` under All, same toolbar plus Lists `MultiSelectDropdown` with Include archived. Chip never saved (`?show=`, read once, `replaceState`). Cards: `ItemCardView` (`components/ItemCardView.tsx`, look shared with `WishlistItem`: cover, badges, name, price) in `ITEM_GRID_CLASSES`, opening the item on its list (`itemDeepLink`), naming the list, actions left to the list page. Sort is a preference saved once picked; new status filters keep both rules. **A changed card stays put** (WIS-297): Reserve, Release, Publish, Mark as…, Move to draft pin it (`useStickyItems`, `lib/hooks/useStickyItems.ts`, over `keepPinnedInPlace`, `lib/utils/stickyItems.ts`) in its slot and in view, even under a non-matching chip, until chip/search/sort change or reload; pinned before the optimistic update (no flicker on failure). A pin only places: always the last-read item (polls land in place) with its own status (owner-folded), chip counts stay true, deleted items vanish.

Product link as a square icon button when not primary ("No link provided" marker if none). "More actions" `Menu` for the rest: owner Mark as received / Mark as not received, Move to draft, Edit on a draft, Mark as most wanted / Not most wanted (sends `{ mostWanted }` alone), last, separated and red, Delete or on a proposal only Decline (review dialog's confirm copy); anyone's Save to my list; omitted if empty. No link: signed-in non-member → Save to my list as primary; owner → **+ link** square opening Edit on Link (`EditItemModal` `initialFocus`); others nothing. Below `sm` (2-col grid): primary + menu only; link square becomes first menu item "Open product page" (`external`, new tab), no-link marker goes, cover opens the sheet. New actions go in the menu unless some role's primary. **Card body opens `ItemSheet`** (WIS-258): the name is a button whose `::after` spans name, price, one-line notes; the cover gets a pointer-only button (no Tab stop, `aria-hidden`; name is the one accessible entry; cover no longer links to the product); action row outside. Shows status via `statusMeta` (owner's never says reserved, no proposer), shop link by domain only if http(s) (`linkDomain`, `lib/utils/itemFields.ts`), and the card's actions from `cardMenuActions` via the card's handlers (thus `onUpdate`), minus the link square; actions opening a page dialog (Edit, Review, Save to my list, + link) close the sheet first. First three = one form, no Save: sticky "Unsaved changes · Discard · Save" bar only while `settingsChanges` would send something; Discard refills from the last-read list. While loading, Items skeleton whatever `?tab=` (role unknown; don't hint tabs); People then shows skeleton rows under its invite form until loaded.

## Item dialogs & forms

- **Adding is one tile and a dialog that can stay open (WIS-242).** Item grid starts with a dashed **Add item** tile (`AddItemTile`) for owners, **Propose an item** for members, none for visitors; opens its header button's dialog. A grid cell (compact on phone, full card from `sm`), only with the grid (not empty state, which offers the add itself; not failed/loading) and only under a chip the new item will show in with no search (`addTileFor`, `lib/utils/listChips.ts`: owner All; member All and Your proposals, whose empty state offers Propose an item). Add/propose footers have **Keep adding** (`ItemFormFooter` `keepAdding`), off on each open, not for copies (Save to my list). On: save clears the form (keeps currency), stays open, refocuses Name; a photo still uploading for the saved item is dropped; each add still uses `mutations.track` and its toast; failed save keeps input. **New list** isn't in the header at any width (WIS-302: signed-in header = "Wishlist." wordmark (`BrandLink`, every width, WIS-319), Home · Reserved · Activity from `sm`, search, avatar); it's the dashboard greeting row's primary button (WIS-252) and beside My wishlists' "Your wishlists" (and its empty state), opening `CreateWishlistModal` in place.
- **Item dialogs share one field order and pinned footer (WIS-256, D10).** `ItemForm`: Name, Product link, Price (amount + shared currency `Select`), Notes, Photo, Most wanted (owners); no Status field (add: Save as draft; review: Add as draft; edit never changes status). `noValidate`: errors under each field via `Field`, focus to first invalid (name, link, price). Buttons outside the form in `BaseModal` `footer` = `ItemFormFooter`, submitting by id (`formId`, `type="submit"` + `form=`). Add: Cancel · **Save as draft** · **Add to list** (Save as draft via `submitItemFormAs`; plain submit is default, so Enter adds as available). Edit: Cancel · **Save**, **Delete item** (`danger-ghost`, confirmed) left. Propose: Cancel · **Propose**, helper "The owners will review it before it's added" atop the form. Review (`ReviewItemModal`, WIS-257, D12), titled "Someone proposed an item", never naming the proposer: Cancel · **Add as draft** · **Add to list** (status from button via `submitItemFormAs`), **Decline** left (confirm "Decline this proposal? It's removed from the list."), deleting via the item's `DELETE` like an owner's delete but only while still a proposal; tells nobody. Use `ItemFormFooter` for new item dialogs. A stored link the schema now refuses shows its error on open; can't save until fixed or cleared. Photo: 72px row (`ImageUpload` `compact`: Add photo, or thumbnail + Replace, Remove); images dropped/pasted anywhere go through the same crop. Scheme-less links get `https://` on blur and save (`normalizeItemLink`, `lib/utils/itemFields.ts`); item schemas normalise the same and refuse non-http(s); `itemChanges` compares normalised. Notes cap `ITEM_NOTES_MAX` (300), counter near it.
- **Wishlist settings send only what the owner changed.** Co-owners edit concurrently and the form fills on load, so a save sends only fields differing from the form as last filled (`settingsChanges`, `lib/utils/wishlistSettings.ts`); otherwise it would overwrite a co-owner (e.g. reopen a list just made private). Each read (reload, save answer) refills untouched fields (`rebaseSettingsForm`). New settings go in `WishlistSettings`. **Account settings likewise** (`profileChanges` / `rebaseProfileForm`, `lib/utils/profileSettings.ts`; two tabs possible): send only changes, each privacy setting separately; `PATCH /api/users/me` writes each by dotted path (`privacy.profileVisibility`), never a rebuilt `privacy` object. Five panels (WIS-265: Public profile, Privacy, Notifications, Preferences, Account; Notifications is `NotificationSettings`, WIS-321: a row per event of `NOTIFICATION_EVENTS` with a `Switch` per offered channel, In app and Email, a dash where one isn't offered; each switch is its own form field `notify.<event>.<channel>` (`NOTIFICATION_SETTINGS`, `lib/utils/profileSettings.ts`) sent as `notificationPrefs.<event>.<channel>`) save each pick immediately (D8): photo, toggle, segmented controls, currency each send only themselves (`profileChanges` vs the profile as last answered), show "Saved" ~2s (`SaveNote`), on failure revert and say so in place. Re-changed mid-save → sent after that save answers, never two in flight. Username, bio and birthday (month + day `Select`s and Clear, `BirthdayField`; a half-picked one holds Save back) are edited: explicit Save / Cancel (phone: sticky "Unsaved changes · Discard · Save" bar); only their unsaved edits arm `useLeaveGuard` (`lib/hooks/useLeaveGuard.ts`: `beforeunload`, plus in-app link clicks held behind "Discard changes?"; back not held). Privacy helpers make claims about search, profile and invite routes; check them when either changes. New account settings go in `ProfileSettings`.
- **Item edits send only what changed, too.** `EditItemModal` fills on open and a co-owner may save meanwhile, so it sends only content fields changed from the form as last filled (`itemChanges`, `lib/utils/itemForm.ts`, given to `onSubmit` with the full payload), and closes with no request if none. Price (amount + currency) is one field; status never in an edit. Above all, an untouched image stays out (sent over a co-owner's replacement it would restore a freed image and free theirs, or be refused as a foreign upload). New content fields go in `ItemContent`. `ReviewItemModal` sends the pressed button's status plus only changed content. **Review acts only on a proposal (WIS-199):** approve (`expectedStatus: 'proposed'` in PATCH body) and Decline (`?expectedStatus=proposed` on DELETE) declare it (`lib/utils/proposalReview.ts`, item hooks' `expectProposal`); `/api/items/[id]` answers 409 `This proposal has already been reviewed` when it isn't one, on first read and as a write/delete condition, identical whatever it became (never reveals reserved). Dialog closes on that 409 (`onError` gets `proposalReviewed`) and once the page's read shows it reviewed or gone (`proposalReviewState`, modal `proposalState` / `onProposalGone`, not during its own request), dropping edits with a toast. **A proposer's edit during review is never approved unseen (WIS-320):** the approve also sends the version it shows (`expectedUpdatedAt`, the item's `updatedAt` as filled); the route answers 409 `PROPOSAL_EDITED_ERROR` with the proposal as it is now (owner-shaped via `serializeItem`), on first read and as a write condition, and the page swaps it into the dialog (`editedProposal`). A poll bringing a newer version does the same (`isNewerVersion`, never older). The dialog then refills untouched fields, keeps the owner's (`ItemForm` `rebaseVersion` → `rebaseItemForm`, price as one field) and shows a warning `Callout`; the retry sends only the owner's changes. Plain owner edit/delete carries no expectation.
