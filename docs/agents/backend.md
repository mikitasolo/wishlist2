# Backend & platform conventions

Server and platform rules, linked from `AGENTS.md`.

## Money, currency & dates

- **Money** is integer **cents**. **Currency codes are stored uppercase** (ISO 4217) everywhere: `Wishlist.currency`, `User.defaultCurrency`, and `Item.price.currency` (Zod and the model uppercase it) and the `Reservation` / `GiftLog` `itemPrice` snapshots copied from it. Normalize a code a client sends with `normalizeCurrency` (trim + uppercase, `lib/utils/currency.ts`) and compare codes through it, never `===` on raw input. The rates map stays keyed lowercase (the rates API's format); only the rates helpers lowercase, at lookup (`rateKey`, `hasRate`, `convertPrice`, `convertToUsdCents` / `convertCurrency`), and a converted price comes back uppercase. Conversion goes through USD (`rate` = units per USD) via `lib/utils/currency.ts` / `currencyRates.ts`. **Others' prices show in the viewer's currency (D9)**: the Prices control starts on the viewer's `defaultCurrency` on someone else's list, on each item's currency on one's own; a pick is remembered per account, separately for own and others' lists, in that browser only (`lib/utils/listPrices.ts`, `useListPrices`); picking the context's default forgets it, and "· your default" is kept as that, not its code, so a new Settings default is followed. Prices is offered only when some priced item isn't in the viewer's currency and once rates have loaded (read only then); otherwise each price shows in its own currency, so the control never names a currency the cards aren't in. **Every price goes through `formatPrice`** (`lib/utils/currency.ts`, `Intl.NumberFormat`: the currency's symbol, grouping, decimals, Latin digits) in `useViewerLocale`'s locale (`lib/hooks/useViewerLocale.ts`): the browser's, but `PRICE_FALLBACK_LOCALE` in a server render and the render hydrating it; server-only code (share card, email) passes none. A converted price shows as `formatApproxPrice` ("≈ €247") over the original on a muted line (`convertedPrice` says when); an unconverted one is exact. The item form's price field is text (`inputMode="decimal"`): `parsePriceInput` takes either separator and grouping ("1 234,50", "1,234.50"), and a lone separator before three digits ("1.234") as the viewer's locale writes numbers, so a typo is refused, not read as 1000× the price; `formatPriceInput` fills and refills it (on blur) in the cards' format; an unreadable amount is refused, never saved as no price.
- **A user's currency is suggested, never guessed.** Accounts start on `defaultCurrency: 'USD'`; the dashboard's one-time prompt (`components/CurrencyPrompt.tsx`: `useCurrencyOffer`, a slim banner under Needs you, WIS-402) offers anyone still on it who hasn't answered (`currencyToOffer`) their browser's local currency. `suggestCurrency` (`lib/utils/currencySuggestion.ts`) runs browser-only, from the time zone then the language's region, suggesting only `CURRENCY_OPTIONS`: no IP geolocation, no server `Accept-Language` guess. A zone naming a place decides alone (a country we don't offer suggests nothing, not the language's); a USD suggestion shows no prompt. Answers, none navigating: **Use PLN**, an **Other currency** `Select` saving on pick, **Keep USD**. `/welcome` asks the same as a Currency row (`useCurrencySuggestion`, preset to the suggestion, shown only while `currencyToOffer` would offer it), sent by Save and Keep, so the prompt never follows on Home. Every answer sends `currencyChosen: true` to `PATCH /api/users/me`, which stamps `User.currencyChosenAt` with the server clock, as for any request setting `defaultCurrency` (so a Settings save changing the currency, when `profileChanges` sends it, is an answer, USD included). The stamp isn't a setting: out of `ProfileSettings`, never sent by the form. It's written with `$min` in the route's one write, so the earliest answer stands and none clears it; hence no default: absent until answered, never null (`$min` would keep null). The session carries only boolean `currencyChosen`. `Wishlist.currency` keeps its schema default, so a list that never stored one stays USD.
- **An occasion's date is a calendar date, not a timestamp.** `Wishlist.occasion.date` is a zone-less `YYYY-MM-DD` and "today" is the viewer's local date, so countdowns are browser-only: read today with `useLocalToday` (`lib/hooks/useLocalToday.ts`; `null` in a server render and the render hydrating it). Do date math with `lib/utils/occasion.ts` (`nextOccurrence`, `daysUntil`, `formatOccasionLabel`, `occasionSortKey`), never via `Date` parsing or `toISOString()` (UTC). **A yearly occasion stores no real year**: `occasionSchema` swaps any year sent (a birth year, say) for `YEARLY_PLACEHOLDER_YEAR` (2000, a leap year so Feb 29 stays valid; `normalizeOccasionDate`), and the model refuses a yearly one on any other year. Never show it: a yearly occasion shows by its next occurrence, and the settings form asks day and month only. A one-off keeps its year and isn't refused once past. An occasion goes to whoever can see its list and never decides who that is.

## Auth & sessions

- **Malformed auth action paths return 404 before Auth.js runs** (`isAuthActionPath`, WIS-454), rather than logging `UnknownAction` into Sentry. Keep its action and provider-path rules in step with Auth.js when upgrading. The sign-in POST refusal still runs first; real auth failures remain reportable.

- **Accounts are created on the first verified sign-in**, by the adapter's `createUser` (`createUserAccount`, `lib/utils/userAccount.ts`, wired in `lib/authAdapter.ts`), never in the `signIn` callback, which also runs on a mere magic-link request. Auth.js sends to `pages.newUser` (`/welcome`, offering to replace the generated username) only if its adapter created the account in that sign-in, so one created earlier skips welcome. That branch also keeps a session the browser held as someone else (the existing-user branch ends it), so `events.signIn` ends it for a new account once its own session exists (`endPreviousSession`, `lib/utils/previousSession.ts`, best-effort). `/welcome` continues to `callbackUrl` only through `safeCallbackPath` (`lib/utils/callbackUrl.ts`, drops off-site); so does the sign-in page for an already-signed-in visitor (never to an `/auth` page, which loops), so they aren't asked for a magic link. A page needing a session sends a signed-out visitor to `signInPath('<its own path>')` with `router.replace`, never home, and lists its path in `AUTH_ONLY_PATHS` (`signInPath` takes nothing else), and may pass its own `location.hash` as `signInPath`'s second argument when the fragment is the payload (`/items/new`, WIS-365: a fragment never reaches the server, so the page carries it through the client redirect; it is only appended to the fixed path, dropped if the callback would pass `CALLBACK_URL_MAX`, and `safeCallbackPath` stays the only gate where the callback is used), which also makes the header's Sign out go home from it rather than reload onto the sign-in form; elsewhere sign-out stays on the page. Links we send (the invite email) point at the page itself, not sign-in. Headed back to a share link (WIS-339), `app/welcome/page.tsx` (server, `force-dynamic`) finds the token in `callbackUrl` (`shareLinkTokenFromCallback`: `/l/<token>` on this origin only) and resolves it as `/l/[token]` does (`resolveLinkForViewer`, `lib/utils/shareLinkPage.ts`: dead or kicked → nothing, a failed lookup spends `shareLinkInvalid`); a live one hands `WelcomeForm` the list's name and the link's level, so it says the list is next and makes Continue as @user_… (Save and continue, once a name is typed) the primary button.
- **The session callback returns an explicit allowlist, never the object Auth.js passes in.** With database sessions that's `{ ...sessionRow, user: userRow }`: returning it or a spread of it puts the raw session token into `GET /api/auth/session` (readable by page scripts, unlike the httpOnly cookie) plus the whole user row; `auth()` returns the same server-side. `sessionPayload` (`lib/utils/sessionPayload.ts`) builds it; add to `SESSION_USER_FIELDS` only with what reads it (tests pin the shape). It's built from the user row the adapter read for that check, with no read of its own (it'd cost every `auth()` a round trip). Every account has a username (`User.username` is required since WIS-357; the adapter's `createUser` generates one at sign-up), so there's no backfill path. `update()` (settings, welcome) is just another check: the row is reread and what the client sends is ignored.
- **The home page is the one page that reads the session on the server** (WIS-269), besides `/l/[token]` and `/welcome` (on its way back to a share link), which read it only to treat a kicked person's live link as dead (WIS-338, `resolveLinkForViewer`) and pass nothing of who it is to the page. The one thing `/l/[token]` takes from that same read is that nobody is signed in (WIS-447): only then is the viewer known to be a visitor, so only then does it read the list's top (`linkVisitorView`: name, owner usernames through `readOwnerUsernames` as the list's `GET` names them, occasion, visibility, banner, description, what that read answers a link visitor anyway) and hand it to `WishlistPage` as `visitorView`, which draws the header and the visitor's note while its own reads load, so the page's LCP text is in the HTML. Its occasion line holds the date and countdown's width, unseen, from the server's date (`todayHint`) until `useLocalToday` knows the browser's, so it doesn't wrap after hydration. Anyone signed in, a session that can't be read, and Preview as visitor get the skeleton as before, and the client drops the view if it finds a session, so an owner or member never sees the visitor's view. `/wishlists/[id]` stays session-free and client-rendered: drawing a visitor's view there would need a server session read. `app/page.tsx` (server component) reads `auth()`, passes it to the browser only via `clientSession` (`lib/utils/sessionPayload.ts`, the `SESSION_USER_FIELDS` allowlist again), and shows `HomeGate`: server-rendered `Landing` signed out, client `Dashboard` signed in. So `/` is dynamic and its HTML is already right: the full landing, or the signed-in header over the dashboard skeleton (the dashboard waits for hydration, `useHydrated`, as its greeting reads the browser clock). `SeededSession` gives that read to everything under it until the root `SessionProvider` has read the session, then steps aside; it overrides next-auth's context value and never nests a second `SessionProvider` (next-auth state is module-wide; the outer one would stay loading). The root layout doesn't read the session (every page would go dynamic); other pages use the session hint (`lib/utils/sessionHint.ts`). The landing has one call to action (**Create your wishlist**, `LandingCta`), the search under it, and a static mock of one list seen by its owner and a friend, made-up data only.
- **A magic link is only sent by the sign-in form's server action** (`requestMagicLink`, `app/auth/signin/actions.ts`): it first checks the Turnstile token (`verifyTurnstileToken`, `lib/turnstile.ts`), then calls Auth.js's server `signIn` inside `asVerifiedSignIn` (`lib/signInEmail.ts`). Auth.js's `POST /api/auth/signin/<provider>` answers 403 (`isMagicLinkSignInPath`), and a request not started inside `asVerifiedSignIn` is refused by the `signIn` callback (`email.verificationRequest`) and `sendVerificationRequest`, so any new way to send a link goes through that action. The link-sent card's **Resend link** (held `RESEND_DELAY_MS`, 30s, after each send) is the same action with a fresh token, so it rechecks and spends the same fail-closed limits; its "Sent to …" is only the address typed on that screen. The subtitle's "to continue to the wishlist you opened" comes from the callback path alone (`signInDestination`, `lib/utils/signInForm.ts`), never a list read; the error page's Try again keeps a `callbackUrl` only via `safeCallbackPath` (`signInRetryPath`). Auth.js puts none on its expired/used-link redirect, so the route's `GET` (`app/api/auth/[...nextauth]/route.ts`) adds the link's own `callbackUrl` to that one redirect (`/auth/error?error=Verification` from `/api/auth/callback/nodemailer` only), reduced by `safeCallbackPath`, dropped if off-site or an auth page (`verificationErrorLocation`, `lib/utils/authErrorRedirect.ts`, WIS-305); nothing else of the link (token, email) is carried, and every other answer passes untouched. Turnstile is on only with both `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` (`getTurnstileKeys`; `lib/env.ts` refuses one alone); the sign-in page reads them per request and passes the site key to the form, so widget and check agree. Only the token can fail it closed, a missing one included, still sent to Cloudflare as an empty response (the form sends none when Turnstile's script couldn't load or run, as in an outage). With no verdict from Cloudflare (unreachable, no answer within `TURNSTILE_VERIFY_TIMEOUT_MS`, a 5xx, `internal-error`, a rejected secret) it fails open and logs `turnstile_unavailable`, the fail-closed sign-in limiters as backstop. Its logs carry no token, IP or email.

## Uploads, images & sharp

- **sharp's native library has to be shipped by hand.** Next's tracing copies sharp's `.node` binding into a bundle but not the libvips it links (`@img/sharp-libvips-<platform>/lib/libvips-cpp.*`), so on Vercel the first `import('sharp')` crashes with `ERR_DLOPEN_FAILED` (WIS-156). `outputFileTracingIncludes` (`next.config.js`) ships libvips with what runs sharp: `/api/upload` and every share card (`opengraph-image`: next/og rasterizes with sharp when loadable; list/profile cards convert their photo with it). `npm run check:trace` (`npm run verify` runs it after the build) fails if a route ships the binding without libvips, one of those ships no binding, or NextAuth's route ships sharp at all. **Email needs no sharp**: its logo is a PNG pre-rendered from `app/icon.svg` (`lib/emailLogo.ts`, `npm run generate:email-logo`; `test/unit/emailLogo.test.ts` fails on drift), so sign-in (NextAuth's route, the sign-in server action) never loads sharp; `test/api/signInWithoutSharp.test.ts` keeps it so, since the sign-in page's trace can't. Pages aren't checked: every page trace carries the binding (Next imports card modules for `alt`, `size`, `contentType`) but never draws a card. A route or page that runs sharp goes into `outputFileTracingIncludes` and check:trace's `RUNS_SHARP`. (macOS Turbopack traces libvips itself; a missing include shows only on Linux, where only the `staging` deploy builds, so run `check:trace` after a build.) Outside `app/api/upload`, load sharp lazily (`await import('sharp')`) inside the function needing it, never atop a widely imported module, so a failure degrades one feature (a card's photo), not the route.
- **Uploads are sanitized and owned.** `app/api/upload` re-encodes every image with `sharp` (strips EXIF/metadata, bakes orientation). **An upload must be its declared type**, since sharp picks its decoder from the bytes, not `file.type`: a mismatch gets the unsupported-type 400, first if the leading bytes lack the declared signature (before sharp reads anything, so only that type's loader sees the file), then if `metadata()`'s format differs (AVIF must be `heif` with AV1 compression, as HEIC shares libheif's loader), before decoding pixels. **librsvg never parses an upload**: before sharp reads anything, whatever the declared type, any file libvips' SVG sniff would claim gets that 400 (`sniffsAsSvg`, mirroring `svgload`'s `is_a`: `<svg`, any case, before the first non-UTF-8 byte, or gzip magic), since a GIF/WebP signature can start one; a test checks it against the bundled libvips' sniff. Checks live in `lib/utils/uploadImageFormat.ts`. Loading an upload route (the block runs in `lib/utils/uploadPipeline.ts`) blocks, process-wide, every libvips loader but JPEG, PNG, WebP, GIF, HEIF and SVG (`UPLOAD_ROUTE_LOADERS`; SVG because next/og rasterizes every card from SVG); other sharp code needing another loader adds it there or fails once the route has loaded. Blobs live under `uploads/<userId>/` against a per-user quota. When an image field (`Item.imageUrl`, `User.image`, `Wishlist.bannerUrl`) is replaced or its record deleted, free the old blob via `lib/utils/blob.ts`, **only ever our own** (`isOwnBlob`: our exact store host, from `BLOB_READ_WRITE_TOKEN`), never a pasted external URL. Free what the write replaced, never what the request read earlier (two concurrent replacers read the same one; freeing it twice orphans a replacement): replace/clear takes the old value from its own write (`findOneAndUpdate`, `returnDocument: 'before'`) into `freeReplacedImage`; an item delete frees what `findOneAndDelete` returned; a list delete does so per item (`deleteOwnedWishlist`, one `findOneAndDelete` per item, reread until none remain, WIS-206), since an item request that read the list earlier can still write after. An edit sending the image the field already holds (`isSameImage`; the review form always does) doesn't write it, or it could restore an already-freed image over a later replacement. **An upload no save took is handed back** (WIS-181): `ImageUpload` stores an image once cropped, before saving, so every form with one passes `uploads` from `useFreshUploads` (`lib/utils/freshUploads.ts`), which sends `DELETE /api/upload` (limited as `uploadRelease`) for an upload made in that form and let go before a save took it: replaced, removed, Discard, the form cancelled/closed/left, or a late upload for a form that moved on (Keep adding). The route frees it only if in the caller's folder and on no record (`releaseUnsavedUpload`, `lib/utils/unsavedUploads.ts`: items, banners, profile photos, reservations, gift logs; new image fields go there), answering the same either way. Check and delete aren't one write, so the browser never hands back one a save may still write (in flight, taken, or failed without a server answer; forms that can't tell, like the item dialogs, treat every failure so); only an answered refusal returns it to the form. An image the form opened with is never handed back. Since records' images get freed, **attach only blobs from your own `uploads/<yourId>/`**: every route writing those fields checks `canAttachImage(next, actorId, current)`, else 400 `FOREIGN_IMAGE_ERROR`. Keeping the record's current value is fine (a co-owner's item/banner upload, a proposer's image on an approved proposal), as are external URLs. Items never share a blob: "Save to my list" (`sourceItemId` on `POST /api/wishlists/[id]/items`) copies the blob into the caller's folder (`copyBlobToUploads`, their quota), saving without it (with a `notice`) if it doesn't fit. A move to another list (WIS-434) copies too, but checks the quota net of the caller's own uploads its deletes free (`replacesSource`, WIS-442): only a blob in their own folder that one moving item holds is credited, and only while they're within the quota. **Snapshots** live under `snapshots/`: once a booking's reservation is written, `snapshotReservationImage` copies the item's image there and points the reservation at it (best-effort; on failure keeps the item's URL), so the gifter's `Reservation` / `GiftLog` image survives the owner deleting or re-imaging the item. Snapshots use nobody's quota (a booking-blind owner's must never move) and fail `canAttachImage`. Free them only via `lib/utils/reservationSnapshots.ts`: `deleteReservations` for a reservation ending without a gift, `releaseSnapshots` when a rebooking replaces one or a gift-log entry is deleted. Marking the gift takes the reservation in one atomic delete and hands its snapshot to the `GiftLog`; a snapshot has one holder at a time, so hand it on atomically or a concurrent dismiss frees what the log shows. Never free a reservation's or gift log's image with `deleteOwnBlob`: older ones (or a failed copy) hold the item's own blob. A few paths still leak a snapshot (a copy landing after booking gave up on it, a killed function, a failed `del()`): `POST /api/maintenance/orphan-snapshots` (operator secret, read-only, `findOrphanSnapshots` in `lib/utils/orphanSnapshots.ts`) reports those no `Reservation` or `GiftLog` holds past a day's grace period (`SNAPSHOT_ORPHAN_GRACE_MS`). Vercel Cron (`vercel.json`, production only) runs `GET /api/cron/sweep-snapshots` monthly (`CRON_SECRET` bearer), which deletes them via `sweepOrphanSnapshots`: never on one scan (marking a gift deletes the reservation before writing its `GiftLog`, and puts it back if that write fails, so a scan in that gap sees a held snapshot as unheld), only after a second holder check `SWEEP_RECHECK_DELAY_MS` later, at most `SWEEP_MAX_DELETIONS` per run. A new holder of snapshots must be added to `heldSnapshots`.

**An image from a URL is re-hosted only by `POST /api/upload/from-url`** (WIS-366, `{ url, page? }`), and that is the one place the server fetches a URL a user gave it: product pages are never fetched (WIS-33), and nothing else may call `fetch`/`undici` on user input. The download goes through `fetchPublicBytes` in `lib/utils/safeFetch.ts` (SSRF guard), whose rules each have a test in `test/unit/safeFetch.test.ts`: `https:` on the default port with no userinfo (`parseFetchableUrl`); every address the host resolves to, or its IP literal, must pass `isPublicAddress` (bytes, not text, so `2130706433`/`0x7f.1` are caught; refuses loopback, RFC 1918, link-local incl. `169.254.169.254`, CGNAT, `0/8`, multicast, reserved, documentation, benchmarking, AS112/AMT/6to4-relay anycast, IPv6 outside `2000::/3`, `2001::/23` incl. Teredo, and IPv4-mapped/compatible/translated, NAT64 or 6to4 addresses embedding a non-public IPv4); the connection is **pinned** to the checked address (IPv4 when the host has one: a pin has no happy-eyeballs fallback) by an undici `Agent` whose `connect.lookup` (`pinnedLookup`) never asks DNS again, so rebinding can't move it, while SNI and `Host` stay the name; redirects are followed by hand, at most 3, each hop checked from scratch and pinned anew; 5 s connect and 10 s total timeouts (DNS, every hop and the body); the body is streamed and dropped past 4 MB (`Content-Length` and `Content-Type` are ignored); requests carry no cookie or user header, only a neutral UA, an image `Accept` and, when `page` is an http(s) URL, its origin alone as `Referer`, sent only to the image's own host, never to a host a redirect leads to. The bytes then pick their type (`sniffUploadImageType`) and go through the same pipeline as a file upload (`storeUploadImage` in `lib/utils/uploadPipeline.ts`, which both upload routes share: signature and SVG checks, sharp re-encode, quota, `put` under `uploads/<userId>/`), answering as `POST /api/upload` does, so the form hands an unsaved one back the same way. **Every failure to get an image out of the URL is the same `{ success: false, error: "Couldn't fetch the image" }`** (400 for a malformed body, 422 otherwise), never the upstream status, body, address or whether the host resolved; only the quota (413), rate limits (429) and a storage error (500) answer differently. The log line is `{"event":"upload_from_url_refused","reason":"<enum>"}`, never the URL or host. It spends `uploadFromUrl` (20 / 10 m, new accounts 5) before fetching, and `upload` only once the bytes are an image, so a URL leading nowhere doesn't use up file uploads; `maxDuration` 30 s. Both upload routes ship libvips (`outputFileTracingIncludes`, `check:trace`).

## Link previews

- **A link preview shows only what a signed-out visitor could see, and is dropped when that changes.** Messengers fetch a link's metadata (`generateMetadata` in `app/wishlists/[id]/layout.tsx`, `app/users/[username]/layout.tsx`) and card (`opengraph-image.tsx`, built in `lib/og/`) signed out, show them to the chat, and keep a copy for good. Both read via `lib/og/data.ts`: a list is named (banner, primary owner, item count) only if `getWishlistViewAccess(list, null)` admits it; else it's `hidden`, answered exactly like a missing list (same card, headers). A profile shows username and avatar, and its bio unless friends-only. A card photo is fetched only from our store (`isOwnBlob`; a pasted URL would let anyone aim the server anywhere), capped in size and time, converted with sharp (lazily; next/og can't draw WebP); the card is a JPEG (`renderCardImage`: photo PNGs run to megabytes, and WhatsApp drops previews much over 300 KB). Bots get the page only once metadata resolves, so every read and the draw are time-boxed (`METADATA_BUDGET_MS`, `DATA_BUDGET_MS`, `PHOTO_BUDGET_MS`, `RENDER_BUDGET_MS`) with a generic fallback; `htmlLimitedBots` (`next.config.js`) is Next's list plus missing preview bots (keep Next's list: the option replaces it). Only a card showing real data, still current once drawn, is cached, only on Vercel's CDN: a day, tagged `og-wishlist-<id>` and `og-user-<primary owner>` (profile: `og-user-<id>`); generic/fallback cards are `no-store`. A list with no banner wears the in-app cover pattern (WIS-428, `coverPatternCardSvg`: laid out as one card-sized `<img>`, since next/og tiles a background image with a seam per tile), picked by the occasion's kind and the name only. So a landed write changing anything a card shows calls `purgeShareCards` (`lib/og/purge.ts`): a list's name, slug, visibility, archived flag, banner or occasion (WIS-428: its kind picks the cover pattern, never its date; `PATCH /api/wishlists/[id]`); its delete; an owner removed, demoted or leaving (`removeWishlistOwner`: may be the primary; adding appends, so never changes it); an item entering or leaving the card's count (added, deleted, published, drafted, approved; `isCountedOnShareCard`); a user's username, bio, avatar or profile visibility (`PATCH /api/users/me`, compared with what its write replaced, `returnDocument: 'before'`, not its earlier read, since another tab's save can land between). The purge deletes, never invalidates (a stale card would be served once more, maybe naming a now-private list), is best-effort, logs no ids. A new card field needs the purge on every write of it. **A share link's preview (WIS-336)** is the one exception to "signed-out visitor": the owner chose to share the link, so `/l/<token>` (`app/l/[token]/layout.tsx`'s `generateMetadata`, `opengraph-image.tsx`, `shareLinkShareCard`) names the list a **live** link opens whatever its visibility, read through `readShareLinkCard` (`resolveShareLink`, which checks the token's shape before any query, then `getWishlistViewAccess(list, null, { link })`); a dead link (malformed, unknown, revoked, expired, its list archived or gone) is `hidden`, the missing list's card, metadata and headers. Its `og:url` is the `/l/<token>` URL, never the list's own (which wouldn't open for the chat). Its card is tagged with the list's tags plus `og-link-<link _id>` (`shareLinkCardTag`; never the token, since tags go to Vercel's purge API), so every list purge above drops link cards too, and revoking a link or editing its expiry purges its tag (`purgeShareCards({ shareLinkIds })`; a label edit doesn't, it isn't on the card). Nothing purges a link that just runs out, so the CDN keeps its card at most `shareLinkCardMaxAge` (a day, capped at the time left before `expiresAt`, measured once drawn), and the cache check (`isShareLinkCardCurrent`) also needs the link still there, still this list's, unexpired and with the expiry it was read with, so a revoke racing the draw isn't cached after its purge. Previews are fetched signed out, so no per-person block applies to them, and they spend no `shareLinkInvalid` budget (crawlers share IPs; the `/l/` page itself spends it).

## Email & logs

- **Emails are a transport plus one template module per email** (WIS-375). `lib/email.ts` is the transport (`deliver`, `EMAIL_TRANSPORT`, the logo attachment, `List-Unsubscribe`) and the `send…` functions callers use (and tests mock as `@/lib/email`); what each email says lives in `lib/emailTemplates/`: `layout.ts` (the shared HTML, `escapeHtml`), `magicLink.ts`, `wishlistInvite.ts`, `birthdayNudge.ts`, and `notification.ts`, which builds every notification email from the copy of its event's module in `notifications/` (one per `NOTIFICATION_EVENTS` event, keyed by event in `NOTIFICATION_EMAILS_BY_EVENT`: a new emailed type doesn't compile without its copy, and a test holds each module to exactly its event's types). Templates are pure: no env, database or send; they get the site URL and the recipient's unsubscribe links through an `EmailContext`. A new email gets a template module, a fixture in `lib/emailTemplates/fixtures.ts` (shown in the gallery and pinned byte for byte by `test/unit/emailTemplates.test.ts`'s snapshots; a deliberate copy change updates them with `npx vitest run -u` in the same diff). **The email gallery** `/dev/emails` renders every fixture, light and dark, with unsigned unsubscribe links and no database read; it exists only where `EMAIL_TRANSPORT=console` may (`isLocalDevRuntime`, `lib/env.ts`: `VERCEL_ENV` unset or `development`, checked per request) and is the app's plain 404 elsewhere, as is the whole `/dev` segment (`app/dev/layout.tsx`; `test/unit/emailGallery.test.tsx`).
- **Email HTML escapes every user-controlled value.** `getEmailTemplate` (`lib/emailTemplates/layout.ts`) escapes its plain fields (title, greeting, button text, URLs); `contentHtml` / `footerHtml` are raw, so pass every interpolated value (wishlist name, display name, address) through `escapeHtml`, or free text can put a live link in mail from our domain. Button and fallback URLs are links we build, never user-supplied (escaping doesn't vet the scheme). **A subject carries no free text**, wishlist name included: escaping can't stop Gmail, Outlook or Apple Mail auto-linking URL/domain-like text, and the inbox shows the subject, so `Claim your gift at https://evil.example/login` would read as our call to action (WIS-102). The invite subject names the inviter by username plus the role (`@ann invited you to a wishlist` / `@ann invited you to co-own a wishlist`, `invitationSubject`), "Someone" without a username (never free-text `name`). The list name appears in the body only inside the sentence naming the inviter (escaped), never on its own line, heading included, since inboxes preview the body's first text (a client may still auto-link it: accepted by the operator over refusing URL-like names). Plain-text parts take raw values, so free text in them must be one line, free of bidi embedding/override/isolate controls (U+202A–U+202E, U+2066–U+2069, which reorder later text, e.g. a domain backwards), and visible: the wishlist name schema (`lib/validations.ts`) refuses line breaks and other control characters, those bidi controls, and names blank once invisible characters are removed (ZWJ/ZWNJ allowed inside a visible name, for emoji sequences and Persian); a new free-text field in an email needs the same. Old rows weren't migrated, so (WIS-293) every free-text value in a plain-text part (or a line composed around one) goes through `isolateForText` (`lib/utils/emailText.ts`): line breaks and control characters become a space, bidi controls are stripped, ZWJ/ZWNJ kept, and the value wrapped in U+2068 … U+2069; HTML parts keep `escapeHtml`.
- **Every notification email carries a one-click unsubscribe** (WIS-321) for its event only: pass the recipient's id to the sender, which builds `unsubscribeUrls` (`lib/utils/unsubscribe.ts`) into the footer (`getEmailTemplate`'s `unsubscribe`, built by `notificationFooter`, also offering Settings) and the text part, and `deliver` sends `List-Unsubscribe` + `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058). The link is an HMAC over purpose, account id and event, keyed from `NEXTAUTH_SECRET` under its own label (no new env var; rotating that secret retires old links), with no expiry. `POST /api/unsubscribe` (signed out; limited per account named, `unsubscribe`, since a mail provider's one-click POSTs share a few IPs, and only links that fail to verify per IP, `unsubscribeInvalid`) sets `notificationPrefs.<event>.email: false` and answers the same whether or not the account exists; it has no GET, and the footer link opens `/unsubscribe`, a page with one button, so a mail scanner opening links unsubscribes no one. Neither names the account or shows its email. The magic link carries none.
- **Notification emails are the in-app row's own line** (WIS-321): `createNotifications` emails, after its rows and its list re-check, everyone whose email setting for the event is on (`emailNotification`, `lib/notificationEmails.ts`; `follow` never, `wishlist_invite` only through `issueWishlistInvite`, `occasion_reminder`, `birthday_reminder`, `gift_reminder` and `gift_nudge` only from their crons; the last two claimed once per person, list and occurrence by `claimOccurrenceEmail`, kinds `gift_reminder` / `gift_nudge`, limited as `emailGiftReminder`, linking to Reserved). `sendNotificationEmail` (`lib/email.ts`, rendered by `notificationEmail` in `lib/emailTemplates/notification.ts`, which holds the actor allow-list `NAMES_ACTOR`) builds the body from `notificationParts` / `notificationLink` on the same fields, so it can't say more than the row: actors only on `join_request` / `invite_accepted` / `link_join` / `wishlist_ask` / `asked_list_made` / `group_gift_joined`, a removal links to Activity, and so does a `wishlist_ask` (WIS-324: the one emailed type about a person, not a list, so it carries no list). A `link_join`'s share link label is owner-written free text: escaped in the HTML, isolated in the text part, never in the subject. Subjects are fixed words plus at most a username. A **proposal**, and a **link join** (WIS-337), each email an owner at most once per list a day (`claimDailyListEmail`, kind `proposal` / `link_join`: a conditional upsert under `NotificationEmailClaim`'s unique index, rolling 24h), and a **group gift join** (WIS-364) a contributor at most once per gift a day (`claimGroupGiftJoinEmail`, kind `group_gift_join`, the gift's id as `key`); the group gift item and list names are free text, in the body only; every kind is limited per recipient (`EMAIL_LIMITERS`, fail-closed `email*` specs); a refused or failed send gives its claim back. A caller whose event can be taken back while its rows are written passes `stillHolds` (the join request: still pending; a link join: its membership still there), checked before any email; one whose recipients can each stop qualifying passes `recheck` (the group gift events: still a contributor and a plain member), which takes back the rows of anyone dropped and emails only the rest. Emails are sent inside the request, so the SMTP transporter has short timeouts (10s connect / greeting, 20s socket). `NotificationEmailClaim` rows expire after 30 days and are removed with the account.
- **Server logs carry no personal data** (anyone with project access reads them). Never log a user's email or id, who is on, left or booked on which list, or a count of someone's bookings; success paths need no log line. Log event and error, reducing an error that quotes its input to its kind (a MongoDB duplicate-key error carries the value, e.g. an email). A record id (invite, wishlist) may stay in a failure line needing it for manual repair, never beside a user id; mask a blob URL's `uploads/<userId>/` folder. `test/unit/noEmailsInLogs.test.ts` catches an email-named value in a `console.*` call; the `smtp` rule (AGENTS.md) and rate-limiter log rules still apply.

## Product analytics

- **Product analytics is Umami Cloud, production only** (WIS-329): cookie-less, so no consent banner. The script loads only where `getUmamiWebsiteId` (`lib/env.ts`) answers an id (`VERCEL_ENV=production` and `NEXT_PUBLIC_UMAMI_WEBSITE_ID` a UUID); the root layout renders `components/Analytics.tsx` only then, and `next.config.js` allows Umami's script and endpoint in the CSP under the same condition (`test/unit/nextConfig.test.ts` keeps them in step). Dev, CI, E2E, previews and staging have no script tag and send nothing.
- **Everything goes through `lib/analytics.ts`**: `track(event, props?)` and the layout's `trackPageView`; no call site touches `window.umami`, and no element gets a `data-umami-event` attribute (the tracker's own click tracking is off with `data-auto-track="false"`, and the before-send hook drops any event not ours). Both no-op while Umami isn't loaded.
- **No URL leaves as it is.** A page view's URL and title are the route pattern (`normalizePath`: `/l/[token]`, `/wishlists/[id]`, `/users/[username]`; no query or hash; any other path is `/[unknown]`), so a share token, an id or a username never reaches Umami; the referrer is our previous page's pattern, or another site's origin only. The tracker's `data-before-send` hook (`scrubPayload`) rebuilds every payload from the allowed fields once more. A new page under `app/` must be added to `normalizePath`'s tables (`test/unit/analytics.test.ts` walks `app/` and fails otherwise).
- **Events are a closed table** (`ANALYTICS_EVENTS`): each event's props are coarse enums (visibility, role, kind, where it came from), never an id, name, username, email, price or currency; an unknown prop or value is dropped, an unknown event not sent. A new event or prop goes in that table, and must say nothing about who or which list.
- **Fire an event only after its write succeeded**: after the server's success answer, never on an optimistic apply, and never for a failed or rolled-back mutation (an item update counts only when `updateItemOptimistically` resolves the server's item). **Never fire a reservation event (`reserve`, `release`, `mark_given`) from an owner's view of a list** (`useReserveToast` counts only for a non-owner), and never send who reserved, joined or left what. Analytics answers to the same rules as the logs.

## Error monitoring

- **Error monitoring is Sentry, production only** (WIS-381, free Developer plan). On only where `getSentryDsn` (`lib/monitoring/config.ts`) answers a DSN (`VERCEL_ENV=production` and `SENTRY_DSN` a well-formed DSN): `instrumentation.ts` imports and starts `@sentry/nextjs` only then, the root layout renders `components/ErrorMonitoring.tsx` only then, and `next.config.js` adds the DSN's ingest host to `connect-src` under the same condition (`test/unit/nextConfig.test.ts` keeps them in step). Dev, CI, E2E, previews and staging load no SDK and send nothing.
- **Errors only**: no performance tracing (not even `tracesSampleRate: 0`, which turns tracing on and adds trace headers to requests), session replay, profiling or session tracking; `sendDefaultPii: false`. Both SDKs take their options from `sharedSentryOptions`.
- **What's reported**: on the server, `onRequestError` (an uncaught error in a page, route handler or server action), process-level crashes, and every `console.error` (`captureConsoleIntegration`), which is how a route's own `catch` that logs and answers 500 is seen; in the browser, uncaught errors and unhandled rejections, plus what `app/error.tsx` and `ErrorBoundary` catch, via `reportError` (`lib/monitoring/browser.ts`; an error with a `digest` came from the server and was reported there; one caught before the SDK has started, as on a page that breaks on first render, is held and sent once it starts). The server adds `dedupeIntegration` (not a Node default), since Next also logs what it hands `onRequestError`. So the logs rule above is also the error-report rule: a `console.error` goes to Sentry.
- **Every event and breadcrumb goes through `scrubEvent` / `scrubBreadcrumb`** (`lib/monitoring/scrub.ts`, `beforeSend` / `beforeBreadcrumb` on both sides): no `user`; the request keeps only its scrubbed URL, method and user agent (no cookie, `Authorization`, `X-Share-Token`, `Referer`, body, query or env); every string (message, exception value, breadcrumb, context, tag, transaction) loses URL queries and fragments (a magic link's token and email, an unsubscribe signature), `/l/<token>`, profile usernames, a list's id or slug, record ids, share-token-shaped words, email addresses and a duplicate-key error's value; `extra` and breadcrumb data also lose any value under a personal key (`email`, `name`, `username`, `token`, `cookie`, `body`…); DOM (`ui.*`) breadcrumbs are dropped, console breadcrumbs keep only their scrubbed message; stack frames keep their source lines but lose `vars`, and a frame's file URL is scrubbed like any URL (inline code names the page's URL). A new way personal data could reach an event (a new header, a context, a tag) gets a rule there and a test in `test/unit/monitoringScrub.test.ts`; `monitoringServerSdk` / `monitoringBrowser` check the real SDKs end to end with a capturing transport. Never call `Sentry.setUser`, `setTag` or `setContext` with a person's data.
- **Bundle cost**: `@sentry/browser` is only imported through `lib/monitoring/browserSdk.ts` (named imports, so replay, feedback and tracing are shaken out), and only by the dynamic `import()` in `lib/monitoring/browser.ts`: a page's up-front JavaScript grows by a few hundred bytes, and the SDK's chunk (about 30 KB gzipped) is fetched only where monitoring is on, after hydration. Don't import `@sentry/*` statically from client code.
- **No source maps are uploaded** (no `withSentryConfig`, so the build never needs a Sentry auth token), so browser stack traces are minified. The server SDK logs one `[Sentry] Failed to register diagnostics-channel injection hooks` line at start: it's about spans, which we don't record.

## Rate limiting

- **Rate limiting goes through `enforce()` / `checkRateLimit()` in `lib/rateLimit.ts`**, never a hand-rolled in-memory counter (Vercel instances don't share it). Add a `SPECS` entry (tokens/window/policy/keyKind) and call `enforce('<name>', key)` right after the auth/access check, returning its response if non-null. A limit guarding one change is spent only by requests making it: `wishlistSlug` (10 per 10 min per user) runs in `PATCH /api/wishlists/[id]`'s slug branch, once the caller is known to own the list and only if the slug differs (`test/api/wishlistSlugLimit.test.ts`). **New accounts get a stricter tier (WIS-42)**: `upload`, `uploadFromUrl`, `invite`, `follow`, `content`, `shareLink`, `joinRequest`, `linkJoin`, `booking`, `listCopy`, `wishlistAsk` have `NEW_ACCOUNT_SPECS` (5 / 10 m, 5 / 10 m, 5 / 1 h, 20 / 1 h, 20 / 1 h, 5 / 1 h, 3 / 1 h, 5 / 1 h, 20 / 1 h, 3 / 1 h, 3 / 1 h; `uploadFromUrl` (standard 20 / 10 m), WIS-366, re-hosting an image from its URL, spent with `upload`; `wishlistAsk` (standard 10 / 1 h), WIS-324, asking a friend for a wishlist; `listCopy` (standard 10 / 1 h), WIS-325, starting a new list from one, spent with `content` since one request copies up to 100 items; `shareLink`, WIS-334, is creating a share link; `joinRequest`, WIS-335, asking to join, which a share link opens to anyone holding it; `linkJoin` (standard 20 / 1 h), WIS-337, joining through a Join link, and `booking`, since a forwarded Join link plus booking-blind owners would let a fresh account reserve a whole list: the item `PATCH` applies it only to a non-owner, once ownership is known) while the first verified sign-in is under 24h old (`isNewAccount`, `lib/utils/accountAge.ts`): the row's `createdAt`, never `emailVerified`, which Auth.js resets each magic-link sign-in (it stands in only without `createdAt`; with neither, the account is new). The session carries boolean `newAccount` (computed each check, so it lifts itself; no route rereads the account), and `enforce` on those limiters requires `{ newAccount: session.user.newAccount }` (type error without it, or with it elsewhere). The tier counts under `rl:<name>:new`, so buckets don't mix as an account ages out; its blocks log and count with `tier: 'new'`. Search and sign-in have no tier; a new limiter on a surface reaching others or costing money gets one. Build keys only with the helpers: **authed** writes `userKey(session.user.id)`, **public** reads `ipKey(request.headers)`, the sign-in email path **both** `emailKey(email)` and `ipKey`. A key's brand must match the entry's `keyKind` (type error otherwise; pass the name as a literal), because each block logs one line `{"event":"rate_limited","name","keyKind"}` for tuning `SPECS`, which, like every limiter log, never carries the key (email, IP, user id). `fail-open` for user-facing reads/writes, `fail-closed` for cost-bearing email sends. A secret a public request presents is limited only when it fails: `unsubscribeInvalid` (a link that doesn't verify) and `shareLinkInvalid` (WIS-335: a share link that doesn't open the list it's sent for, per IP, from `admitListViewer` and the `/l/` page), so a valid one shared by many people behind one IP is never throttled. The policy covers store **timeouts** too: on slow Redis `@upstash/ratelimit` resolves `{ success: true, reason: 'timeout' }` after `STORE_TIMEOUT_MS`, which `run()` treats as an error, so never act on the SDK's `success` outside `run()`. Limiting is **disabled** without `UPSTASH_REDIS_REST_URL`/`_TOKEN` or the `KV_REST_API_URL`/`_TOKEN` fallbacks (CI/tests; tests inject a fake via `__setRateLimiters`). A `.env` pulled from Vercel has the `KV_*` pair, so local dev _does_ rate-limit against that store.

## Migrations

- **Schema migrations are HTTP endpoints** at `app/api/migrations/<name>/route.ts`, built with `createMigration` (`lib/utils/migration.ts`), gated on the `X-Migration-Secret` header: `curl -X POST -H "X-Migration-Secret: $MIGRATION_SECRET" <host>/api/migrations/<name>`. In the tree now: `sync-hot-query-indexes` (WIS-377, run after its deploy; delete it once it has run everywhere). Earlier ones ran everywhere and were deleted (the co-ownership set, `dedupe-pending-invites`, `relabel-answered-invite-notifications`, `uppercase-currency-codes`, `backfill-usernames`; see git history). A new one:
  - Is **idempotent**: re-running is free and finishes a partial run.
  - States its **deploy ordering** in the docstring. _Additive_ (only writes new fields) is safe before the deploy; one removing or moving data old code depends on runs **after**, or it breaks the running deployment.
  - Gates any reader fallback for the un-migrated shape on the new field being absent, and deletes it in a follow-up once run everywhere; never leave fallbacks behind.
  - For a new **unique index** on a collection that may hold duplicates, dedupes and then builds it (`Model.createIndexes()`): `autoIndex` is on (`lib/mongodb.ts` leaves it) but fails such a build silently (the error only hits the model's `'index'` event), so the index never appears.
  - **Drops an index** taken out of a schema (autoIndex builds new indexes but never drops one), found by its key, after the deploy: the old code's autoIndex would rebuild it.
- **Hot queries stay index-backed** (WIS-377): `test/api/indexAudit.test.ts` runs each hot path (the list access filter, search, a list and its items, `resolveShareLink`, the dashboard and Coming up, a profile's lists, your own items and gifts, the Activity feed, the three crons, group gift and reservation reads) with the profiler on and fails on any `COLLSCAN`, naming the collection and filter (it can't see a `$lookup`'s inner reads, so keep those on `_id`). A new hot query gets a scenario there; one that scans gets an index, not a query rewrite, where an index will do. The same file fails on a plain index whose keys lead another full index (it only costs writes).
- **Maintenance endpoints** (`app/api/maintenance/<name>/route.ts`) use the same `createMigration` secret gate for operator tools that stay in the tree, like the orphaned-snapshot report. They are read-only unless their docstring says otherwise. **Cron jobs** live at `app/api/cron/<name>/route.ts` as `GET` handlers checking `Authorization: Bearer $CRON_SECRET` (`secretsMatch`), scheduled in `vercel.json` `crons` (Hobby: at most daily, loose timing, no retries; pinned by `test/unit/vercelConfig.test.ts`), behind `cronRefusal` (`lib/utils/cronAuth.ts`). **Each cron pings its own healthchecks.io check** (WIS-382) through `pingCronHeartbeat` (`lib/utils/cronHeartbeat.ts`), only after a wholly successful run (a birthday task or the dead-move settling throwing counts as a failure), its URL from its `HEALTHCHECK_URL_<NAME>` (`CRON_HEARTBEAT_ENV_VARS` in `lib/env.ts`, https only (anything else is a startup warning, never an error, and pings nothing), unset ⇒ no ping; a test keeps it in step with `vercel.json`); the body is the run's counts only (`countsOnly`), and a failed or slow ping (3 s timeout) is logged by the cron's name, never the URL, and changes nothing about the run. A new cron gets an entry there and a ping. A daily job that must not miss a day gives itself a catch-up window and is idempotent per thing it does, as `GET /api/cron/occasion-reminders` is (06:00 UTC), `GET /api/cron/birthdays` (06:15 UTC) and `GET /api/cron/gift-reminders` (06:30 UTC, WIS-384; see the invariants for all three), which first settles everyone's dead item moves (WIS-443, `settleAllDeadMoves`: capped, on its own 10 s budget after which it takes back no more copies (a row cut short is kept for the next run), a failure logged and the reminders sent anyway). Add a small maintenance job to an existing cron like that before adding a cron. **Every job about profile birthdays runs in that one cron** (`runBirthdayTasks`, `lib/utils/birthdayCron.ts`): each task in `BIRTHDAY_TASKS` gets its own time budget (a deadline it checks before starting new work; the budgets add up to at most `BIRTHDAY_CRON_TOTAL_BUDGET_MS`, under the 60s) and its own caps, and one that throws doesn't stop the next; add a new birthday job there, not as a new cron. **Notification preferences** live in `User.notificationPrefs.<event>.<channel>` (`lib/utils/notificationPrefs.ts`), channels `inApp` and `email`. `NOTIFICATION_EVENTS` is the one table (operator decision, WIS-321): each event's notification types (`access_changed` covers `role_changed` and `removed_from_wishlist`), and per channel offered its default: in-app on for all; email on for `wishlist_invite`, `occasion_reminder`, `join_request`, `link_join` (WIS-337), `proposal`, off for `gift_reminder` and `gift_nudge` (WIS-384), `birthday_reminder` (WIS-345), `wishlist_ask` and `asked_list_made` (WIS-324), `access_changed`, `invite_accepted`, `proposal_approved`, and **none for `follow`** (stranger-triggerable). `birthday_nudge` (WIS-344) covers no notification type and is offered by email only (on): its in-app side is a Needs you row, dismissed there; its email is `sendBirthdayNudgeEmail` (`lib/email.ts`, template `lib/emailTemplates/birthdayNudge.ts`), limited as `emailBirthdayNudge`, claimed once a year (`kind: 'birthday_nudge'`, no `wishlist`). The User schema and `notificationPrefsSchema` are built from it. Never stored as a default: a missing setting reads as its default through `wantsNotification` / `notificationOptInFilter`, so a new event or channel is added there with no migration. `createNotifications` skips recipients whose in-app setting is off; a sender checks the email setting when it sends, through `recipientsWanting` (`lib/notifications.ts`; a failed read keeps the default's answer in app, and emails nobody). `PATCH /api/users/me` writes each by its dotted path (`notificationPrefWrites`); `notificationPrefsSchema` refuses unknown events and channels.
